# Taproot design

Taproot is a fork of CLIProxyAPI. It runs on one server and serves every Claude and Codex account to its owner's tailnet through one endpoint, with one dashboard that covers credentials, quota, usage and cost, request logs, and backups.

This document records how taproot is built and why: which upstream files it changes, its security model, each module's design and the measurements behind it, the `/taproot/api/v1` contract, and the dashboard's scope. Update it in the same change as the code it describes.

## Goals

- Taproot is a service with its own data. The code has no importer and no migrations (see "Decisions"). When it replaces another proxy, that proxy is stopped before its auth files are copied in, so the two proxies never refresh the same OAuth tokens.
- Only tailnet devices that were given Proxy or Admin reach the proxy, or the management API and the dashboard. Nobody types a key or password.
- The dashboard has no Quick Start, AI Providers, sponsor or affiliate content, Kimi China, Devin, Vertex, SIWC, or config API-key editing.
- Quota, on the Accounts page: pooled remaining percentage per provider as a chart of recorded and projected lines, with large figures for pool empty, first empty, next reset, and burn rate over 1h, 3h, or 6h.
- Usage section: cost, requests, tokens including cache reads and writes, latency, time to first token, and failures, broken down by account, model, and session.
- Request logs are compressed, indexed, searchable, and pruned to a budget. Backups run on a schedule, and you can download or restore them from the dashboard.
- Upstream merges stay cheap. See "Upstream boundary".

## Upstream boundary

- The Go module path is `github.com/265866/taproot`. Upstream's is `github.com/router-for-me/CLIProxyAPI/v8`.
  - `scripts/taproot/rewrite-module-path.sh` rewrites the one into the other in every tracked `.go` file, `go.mod`, and `go.sum`, and re-sorts imports with `gofmt`. A path without a `/vN` suffix takes only v0 or v1 versions, so nested modules that require the root (`examples/plugin/*/go`, which replace it with a local directory) get `v0.0.0`. The rewrite must stay deterministic: the merges below depend on it giving the same output for the same input.
  - `gofmt`'s output differs between Go releases, so the rewrite runs the `gofmt` of the toolchain that the rewritten tree's `go.mod` names (its `toolchain` line, else its `go` line), through `GOTOOLCHAIN`, and never the installed Go's. Measured on upstream `6e6afab99`: Go 1.27.1's own `gofmt` gave a tree that differs from `55411c966` in 3 files, and `go.mod`'s go1.26.10 reproduces `55411c966`'s tree byte for byte, with Go 1.27.1 installed.
  - `scripts/taproot/check-rewrite.sh [commit]` reruns the rewrite on the upstream commit of the newest snapshot in a commit's history and fails unless the result is the snapshot's tree. The sync script runs the same check on the previous snapshot before it builds a new one, because a rewrite that no longer reproduces it would also change, in the new snapshot, lines upstream never touched.
  - The rename commit went through that rewrite, and its second parent is upstream `6e6afab99` put through the same rewrite. That snapshot commit carries a `Taproot-Upstream: <upstream commit>` trailer. The first sync merged snapshot `cd61d2911` (upstream `681ce41b6`, 96 commits after `6e6afab99`). Its merge commit and every snapshot must stay in history: merge a sync's PR with a merge commit, never a squash or rebase, or the next sync finds no snapshot and merges against the wrong base.
  - `scripts/taproot/sync-upstream.sh` fetches `upstream/main`, rewrites its tip in a temporary worktree, and commits the result to the staging branch `taproot/upstream`. The staging commit has two parents: upstream's tip and the previous rewritten snapshot. The script finds that snapshot as the newest commit in HEAD's history whose `Taproot-Upstream` git trailer (parsed by git, so a line elsewhere in a message does not count) names its first parent, and whose second parent, if it has one, is a snapshot too. The script then merges the staging branch. The merge base is the previous snapshot, which already has the new path, so upstream's changes arrive with the new path and only real conflicts remain. A plain merge of upstream would instead conflict wherever upstream touched an import block.
  - Tested in a throwaway clone with two simulated upstream commits that added and changed imports in a file taproot edits (`cmd/server/main.go`), in a file taproot never touched, and in a new package, and that changed the deleted `Dockerfile`. Both merged with no import conflicts and no old path left, and the `Dockerfile` stayed deleted. A plain merge of the first commit conflicted in both Go files.
  - Plugins do not depend on the path. The host loads a native plugin over a C ABI: `dlopen`, the `cliproxy_plugin_init` symbol, the ABI version from `sdk/pluginabi`, and method names with byte buffers. No Go package path crosses that boundary, so plugins built against upstream's module path, such as Claude Keep Rolling, load unchanged. Checked by loading the `codex-service-tier` example, built from upstream `6e6afab99` with the old path, into the renamed image: the host loaded and registered it and read its metadata.
- Fork code lives in `internal/taproot/**`. Apart from the module-path rewrite and the small hooks listed below, the upstream files it edits are `cmd/server/main.go`, with the taproot calls and exit codes listed below, `internal/cmd/run.go` (exit codes, below), and `internal/tui/client.go`, which sends `X-Taproot-Request: 1` on every request (one line; see "Security model"). Any further upstream edit needs a written reason in this file.
  - `scripts/taproot/check-upstream-boundary.sh [commit]`, a step of CI's `go` job and of the sync script's checks, keeps this section complete. It diffs the commit against the newest snapshot in its history and fails on any changed path outside taproot's own (`internal/taproot/`, `web/`, `scripts/taproot/`, `examples/taproot/`, `docs/`, `.github/`, `nix/`, `licenses/`, and taproot's top-level files) that this section does not name in backticks. An edited or added file needs its own entry; a deleted one may instead fall under a named directory (`assets/`) or glob, whose `*` does not cross a `/`. A new fork-owned location goes in the script's `fork_owned` pattern. `scripts/taproot/scripts_test.go` covers it.
  - `CheckServerMode` (launch audit S4) makes the binary exit before Home mode (`-home-jwt`) or `--tui --standalone` starts a server. Both paths start the server without reaching `taproot.Setup`, so without the guard. The call sits right after the flags and `HOME_JWT` are read, about 4 lines, so a Home JWT is refused, with exit status 1, before main parses it, fetches config or plugins from Home, or starts anything (review finding 8). A TUI client given a Home JWT is refused too, because main contacts Home before it knows the mode. The `if !homeMode` that used to wrap `Setup` is gone because Home mode no longer gets there.
  - `taproot.HandleArgs(os.Args)` (one line) runs right before `flag.Parse`, after upstream defines its flags and its own help text, so the help it sets wins. It serves `--version`, which prints `taproot <version> (commit <c>, built <date>)` and exits 0, and replaces the help text with one that leaves out the flags that do not apply to taproot (`-home-jwt`, `-home-disable-cluster-discovery`, `-standalone`, `-password`, and the login and import flags of the providers the dashboard dropped: `-kimi-login`, `-devin-login`, `-vertex-import`, `-vertex-import-prefix`, `-siwc-bind`). Those flags stay defined, so upstream's flag code is unchanged. It reads `--version` the way the flag package would, so a flag value or an argument after `--` is not taken for it. If upstream or a plugin defines its own `version` flag, taproot leaves it and its `--version` alone. It is also where the default config files are written on first run (see "First run" under "Architecture"), because that must happen before upstream reads `--config`, and it needs no upstream edit of its own.
  - `taproot.Setup` returns a shutdown function, and `main` calls it after `cmd.StartServiceWithPluginHost` returns (one changed line and one added line). It cancels taproot's modules and waits for the request-log writer and for ingest's final flush, then exits with status 75 when a restore asked for a restart (see "Shutdown drain" and "Backups"). No taproot code runs at that point without the call: upstream's SDK `Hooks` cover start only, `Server.Stop` closes the HTTP server without draining, and `main` returns, ending the process, as soon as the service stops, so a taproot signal handler would race it. Without the call, a SIGTERM lost request-log records in 4 of 7 measured trials and every usage event of the last second. `cmd/server/taproot_cli_test.go` sends requests through a fake upstream, signals the child process, and counts the stored records, and checks the exit status after a restore.
  - The three `CLIProxyAPI Version: ...` lines (the `discover` subcommand's banner on stderr, the startup banner on stdout, and the startup log line) print `taproot.VersionLine()` instead (3 lines). The stdout banner moved from before the flag definitions to right after `HandleArgs` (3 lines), so `--version` prints its line once and the help starts with the version. The provider `User-Agent` (`CLIProxyAPI/<version>`) stays upstream's.
  - Upstream logs a fatal startup error and returns from `main`, which exits 0, so a supervisor such as systemd's `Restart=on-failure` treats a server that never started as a clean stop. 17 of those returns are `os.Exit(1)` (one line each): the working directory, the Postgres, object, and git stores, the config load, the log output, and the auth directory. The Home-mode returns stay, because `CheckServerMode` exits before Home mode reaches them. `internal/cmd/run.go`'s `StartServiceWithPluginHost` exits 1 when the service fails to build or `Run` returns an error other than a cancel (2 lines plus the `os` import): a port that is already in use used to exit 0 there. `cmd/server/taproot_cli_test.go` runs `main` in a child process and checks `--version`, the help, and exit status 1 for a config that does not parse, a missing `taproot.yaml`, a missing tailscaled socket, and a port in use.
  - The tests of the `main.go` and `client.go` edits are taproot files in upstream's packages: `cmd/server/taproot_mode_test.go` checks that a Home JWT is refused before main contacts Home, and `internal/tui/taproot_request_header_test.go` checks that the TUI client sends `X-Taproot-Request: 1`.
- The removed providers come out of the dashboard only. Their backend code stays, because deleting it would conflict with every upstream merge.
- `web/` is a hard fork of Cli-Proxy-API-Management-Center at `f154fa9`, imported with `git subtree`. The fork stops following upstream UI changes. It follows the backend's management API instead.
- `scripts/taproot/sync-upstream.sh` merges the rewritten `upstream/main` (see above) and runs the checks of CI's `go` and `web` jobs, except the Go version, golangci-lint, and govulncheck steps: `gofmt` from `go.mod`'s toolchain, `go build ./...`, `GOOS=linux go vet ./...`, `go test ./...` without `TestAdvertiserAndBrowser_Integration` (it needs real mDNS multicast), `scripts/taproot/check-upstream-boundary.sh` on the merge commit, and `bun install --frozen-lockfile` and `bun run verify` in `web/`, then, when Nix is installed, refreshes the flake's hashes (see "Nix"). `--checks-only` runs the same checks on HEAD. CI's codec and image jobs stay in CI, because they need cargo and a container engine, and a sync does not change the Rust code or the Containerfile.
  - The scripts share `scripts/taproot/upstream-lib.sh`. `scripts/taproot/scripts_test.go` drives them against throwaway repositories: the snapshot search, the rewrite check, the flagged new files, and a merge that runs the checks. CI's `go test ./...` runs it, and so does the sync script's.
- Taproot types that implement an upstream interface assert it at compile time, so a sync that changes the interface fails to build at the type: `reqlog`'s `requestLogger` (`logging.RequestLogger`) and `streamWriter` (`logging.StreamingLogWriter`), `ingest.Ingest` (`usage.Plugin`), and `routing.SoonestResetSelector` (`coreauth.Selector`). Upstream also finds some request-logger methods through anonymous interfaces, such as `interface{ SetEnabled(bool) }` and `WriteAPIRequestSource`, which no assertion can name. `internal/taproot/reqlog/upstream_methods_test.go` requires taproot's logger and stream writer to have every exported method of upstream's `FileRequestLogger` and `FileStreamingLogWriter`, with the same signature, except the Home-only `SetHomeEnabled`.
- Taproot deleted upstream files a stranger would mistake for taproot's (launch audit S1 and S2): the GitHub workflows, funding file, issue template, and catalog-refresh script under `.github/`; `Dockerfile`, `docker-compose.yml`, `docker-compose.cluster.yml`, `docker-build.sh`, and `docker-build.ps1`; `README_CN.md`, `README_JA.md`, the sponsor images in `assets/`, and the provider logos in `assets/logo/`; `.env.cluster.example`, which configured Home mode (taproot refuses it), and `.env.example`, which listed the Management password and the remote stores (taproot sets the password itself, is tested only with local files, and documents its own two variables, `TZ` and `TAPROOT_CONFIG`, in `docs/configuration.md`); the upstream SDK guides in `docs/`; and the Management Center's READMEs, logo, and workflows under `web/`. `.github/workflows/ci.yml`, `.github/workflows/renovate-refresh.yml`, the release workflows (`.github/workflows/release-please.yml` and `.github/workflows/release.yml`, with release-please's `.github/release-please-config.json` and `.github/.release-please-manifest.json`), and `Containerfile.taproot` replace them, and taproot's own issue forms (`.github/ISSUE_TEMPLATE/*.yml`, which do not reuse upstream's `bug_report.md` name) and `.github/pull_request_template.md` replace the issue template. `CLAUDE.md`, a one-line `@AGENTS.md` import, is deleted too: Claude Code 2.1.277 and later reads `AGENTS.md` itself.
  - When upstream changes a file taproot deleted, the merge stops on a modify/delete conflict. The sync script resolves those as "keep deleted" (`git rm`) and stops on every other conflict. `--dry-run` lists both kinds. A file upstream deleted that taproot changed is still a conflict for a person to resolve.
  - A new upstream file of a kind taproot deletes stops the merge before its commit, and `--dry-run` lists it, so a person keeps it or deletes it with `git rm`. The kinds are anything under `.github/` or `assets/`, a top-level `docs/*.md`, `README_*.md`, or `.env*` file, and top-level Docker build files (`Dockerfile*`, `*.Dockerfile`, `docker-build*`, and `docker-compose*` or `compose*` YAML). The pattern is `deleted_categories` in `scripts/taproot/upstream-lib.sh`. Taproot keeps some files of these kinds (its own guides in `docs/*.md`, upstream's `docs/lan-discovery.md` and `docs/management-api-v8.md`, `.github/workflows/ci.yml`, `.github/workflows/renovate-refresh.yml`, the release workflows and release-please files, its issue forms, and `.github/pull_request_template.md`), so the script asks rather than deleting. An upstream file added at one of those paths, such as `.github/ISSUE_TEMPLATE/config.yml`, is an add/add conflict, which the sync also stops on; keep taproot's file. Upstream `681ce41b6` added `docs/codex-refresh-recovery.md`, a guide to upstream's Codex refresh journal, and the sync that merged it deleted the file, like the other upstream guides in `docs/`.
- Taproot rewrote some of upstream's repository files for itself: `README.md`, `AGENTS.md` (a pointer to `CONTRIBUTING.md`), `LICENSE` (one added copyright line), `.gitignore`, and `.dockerignore`. When upstream changes the lines taproot changed, the sync stops on a conflict. Keep taproot's text. When an upstream change to its `AGENTS.md` adds a rule for code taproot changes, copy the rule into `CONTRIBUTING.md`.
- The top-level `licenses/` directory is taproot's; upstream has no such path. It holds the GNU LGPL v3 and GPL v3 texts, unchanged from gnu.org, for the LGPL crates in the codec library (see "LGPL crates" under Decisions). `.dockerignore` no longer excludes `LICENSE`, because the image ships it.
- `go.mod` requires `github.com/klauspost/compress` v1.20.3, not upstream's v1.17.4. Request-log segments and blobs compress at `SpeedBestCompression`, and v1.17.4 writes corrupt frames there for some inputs (fixed in v1.17.6, "zstd: Fix incorrect repeat coding in best mode"): one of 107 real PNG image streams failed its own CRC on v1.17.4 and none on v1.20.3. A sync that brings upstream's line back conflicts here; keep the higher version.
  - `internal/api/middleware/request_logging_test.go` gains `zstd.WithSingleSegment(true)` in `TestCaptureRequestInfoDoesNotDecodeASingleSegmentBomb` (one option). The test's bomb was single-segment in name only: v1.17.4's best level happened to pick a 32 MiB window, which the middleware's 8 MiB bound refused, while v1.20.3 picks 8 MiB and the frame decodes up to the capture limit. Real single-segment frames are refused on both versions, so the middleware is unchanged and the option makes the test build the frame it is named for.
- `go.mod` adds a `toolchain go1.26.11` line under upstream's `go 1.26.10` (one line). Go 1.26.10's `net/http` can crash an HTTP/1 server through a `MaxBytesReader` header race (GO-2026-6859, fixed in 1.26.11), and `govulncheck` fails CI on it. A `toolchain` line, unlike a new `go` line, raises the toolchain CI (`setup-go` reads it) and `Containerfile.taproot`'s `GO_VERSION` use without raising the minimum Go that builds taproot, so the Nix package still builds with nixpkgs' Go 1.26 (with nixpkgs' own patch level). Drop the line once upstream's `go` line reaches 1.26.11; a sync that changes that line conflicts only here. Go 1.26.11's cgo also refuses to link an archive that carries LLVM bitcode sections (`.llvmbc`, `.llvmcmd`), which the codec library gets from the Rust toolchain's precompiled `compiler_builtins` and from zstd's assembly, untouched by LTO. Every build of `libtaproot_codec.a` (the image, CI, the release workflow, the Nix package, and CONTRIBUTING's steps) removes those sections with `objcopy` after `cargo build`; they hold only bitcode for link-time optimization, so the native code is unchanged (the codec tests pass on the stripped archive).
- `go.mod` requires `github.com/andybalholm/brotli` v1.2.8, not upstream's v1.0.6 (one line, plus `go.sum`). Before v1.2.7, the decoder's allocations are not bounded by its input, so a small crafted stream can allocate hundreds of megabytes (GO-2026-6888). The server calls it: `internal/runtime/executor/helps/response_decode.go` and `internal/auth/claude/oauth_response.go` decode brotli-encoded provider responses, and CI's govulncheck step fails on v1.0.6. A sync that changes upstream's line conflicts here; keep the higher version.
- `go.mod` requires `modernc.org/sqlite` v1.62.0, the cgo-free SQLite driver that `internal/taproot/store` opens `taproot.db` with, and its indirect dependencies `modernc.org/libc` v1.80.1, `modernc.org/mathutil` v1.7.1, `modernc.org/memory` v1.12.1, `github.com/ncruces/go-strftime` v1.1.0, and `github.com/remyoudompheng/bigfft` at a 2023 pseudo-version (six added lines).
  - Minimal version selection raises four of upstream's requirements to the versions `modernc.org/libc` and `modernc.org/sqlite` require (`go mod graph`): `golang.org/x/sync` v0.23.0 to v0.24.0, `golang.org/x/sys` v0.48.0 to v0.49.0, `github.com/dustin/go-humanize` v1.0.1 to v1.1.0, and `github.com/mattn/go-isatty` v0.0.20 to v0.0.24 (four changed lines). A sync that changes these lines conflicts here; keep the higher versions.
- `go.sum` changes with `go.mod` (+54/−13): the hashes of the compress and brotli modules above, the SQLite modules and the rest of their module graph (`go.mod` hashes of modules such as `golang.org/x/tools` and `modernc.org/ccgo/v4`), and the bumped versions. Resolve a conflict in it by running `go mod tidy` on the merged `go.mod`, not by hand.
- `sdk/cliproxy/service_config.go` maps `routing.strategy: soonest-reset-first` to `internal/taproot/routing.SoonestResetSelector` (7 lines).
  - Upstream builds the credential selector only there, and `routing.session-affinity` wraps whatever it builds.
  - The plugin-scheduler hook would bypass session affinity, and the plugin host overwrites it.
- `internal/api/protocol_multiplexer.go` gains a package-level RESP connection filter (`SetRESPConnectionFilter`, `RESPConnectionAllowed`, 28 added lines). The multiplexer consults it before a Redis-protocol connection reaches `handleRedisConnection` and closes a refused connection before any reply. Taproot's `Setup` installs `access.RESPFilter`, which admits loopback only.
  - Upstream serves its RESP usage queue on the proxy port outside gin, so the guard never sees it, and the guard's generated `MANAGEMENT_PASSWORD` turns on remote `AUTH` there. Without the hook, any host that reaches the port could `AUTH` with the management secret or a `config.yaml` `secret-key` and drain the usage and error queues.
  - No server option or middleware runs at that point, so a package-level hook is the smallest seam. `internal/api/taproot_resp_filter_test.go` drives it through the real multiplexer.
- `internal/pluginhost/taproot_caller.go` is a new file (no upstream file changes) that exports `CallerPlugin(ctx)` and `(*Host).PluginName(id)`, 30 lines.
  - A plugin that calls `host.model.execute` runs the model in-process, so no HTTP request carries a device. The host tags the callback context with the plugin's ID under an unexported key, and usage records reach ingest with that context. `CallerPlugin` reads the key; nothing else exposes it.
  - `PluginName` reads the active plugin's metadata name. Upstream's `RegisteredPlugins` also calls into each plugin for OAuth and quota identifiers, which ingest's flush must not do.
  - Wrapping the host's model executor instead would need no new file, but upstream resets the executor on every config reload (`internal/api/server_reload.go`).
  - `internal/pluginhost/taproot_caller_test.go` drives `host.model.execute` and checks the context the model executor receives.
- Four hot-path speedups in upstream files, measured by replaying production Claude Code bodies through a loopback server and fake Anthropic upstream. Each belongs upstream too; a sync that touches these lines conflicts until then.

The strip's indexed `Doc.Get` rescans every earlier message, so sanitizing was quadratic in request size. Upstream bytes are unchanged on 18 real bodies.

## Soonest-reset-first routing

- **Order.** New sessions and failovers go to the eligible account whose weekly window resets soonest:
  - Claude uses `anthropic-ratelimit-unified-7d-reset`.
  - Codex uses its 10080-minute window.
  - Weekly resets are fixed per account, so a past reset rolls forward by whole weeks.
- **Skipped and unknown accounts.** Accounts at or above 100% weekly utilization are skipped. Accounts with no known weekly reset sort last. Resets less than a minute apart tie, because Codex reports a relative reset that can differ by a second between accounts, and ties use round-robin.
- **Session affinity first.** Bound sessions keep their account.
- **Taproot's own readings.** Upstream keeps quota headers in memory only. When an account's headers have no weekly window, routing uses the newest weekly reading in taproot's quota store: `Setup` seeds `routing.Stored` from `LatestQuota` and keeps it current through `Ingest.OnQuota`, which includes the idle-account poller's reads. So after a restart, accounts with history are ordered at once.
- **Probing.** A Claude or Codex OAuth account with no observed headers and no stored reading gets a new session first, so its reset becomes known. Without that, the first account to answer would take every session. A probe that records nothing, such as a `count_tokens` request, a 5xx, or a dropped connection, is repeated after 10 minutes, so the account is not left out until the next restart. API-key accounts report no weekly window and are not probed.

## Architecture

`taproot.Setup` (in `internal/taproot/taproot.go`) reads `taproot.yaml` from beside `config.yaml`, or from the path in `TAPROOT_CONFIG`. Taproot's settings stay out of `config.yaml`, which upstream owns: upstream's loader silently ignores keys it does not know (`bogus-key: 1` loads without error), so a taproot key there would do nothing, and upstream already has its own `access` section. Taproot decodes `taproot.yaml` strictly too: an unknown key stops startup with its name, so a misspelled access setting cannot fall back silently. So does a second YAML document after a `---` line, which the decoder would otherwise ignore; a lone `---` before the first and empty documents after it are allowed. A missing `taproot.yaml` beside an existing `config.yaml` stops startup with the path Setup looked for (see "First run" for why). Setup then opens the modules and returns `api.ServerOption`s:

- `WithMiddleware(guard.Middleware(), web.Middleware(), apiNotFound(), clientRequests(usage), accounts.middleware())`. `web.Middleware()` serves the dashboard at `/`, because upstream registers its own `GET /` before router configurators run. `apiNotFound()` answers a request under `/taproot/api/v1` that matches no route with the API's JSON 404 (see the API contract): gin runs global middleware before upstream's no-route handler, which answers an empty 404, and leaves `FullPath` empty for such a request. `clientRequests` records client requests (see "Client requests" under "Ingest"); it runs after the guard, so a refused request is never one, and outside the no-accounts middleware, so it sees the rewritten error.
- `WithRouterConfigurator(...)`, which mounts `/taproot/api/v1/*`
- `WithRequestLoggerFactory(...)`

**First run.** When the file `--config` names does not exist, `taproot.HandleArgs` (`internal/taproot/firstrun.go`) writes it before upstream's `main` reads it: the content of `examples/taproot/config.yaml`, with `auth-dir` moved to `auths/` beside the new file. `TestDefaultConfigMatchesExample` keeps the copy in Go equal to the example. Where Setup will look for `taproot.yaml` (beside `config.yaml`, or `TAPROOT_CONFIG`), it writes one with an empty `access` section and comments that explain the setup code. It creates the directory if needed, writes every file with mode 0600 and `O_EXCL`, so it never replaces a file, and logs each path it wrote. It writes `taproot.yaml` first: a run that fails before `config.yaml` exists leaves a first run for the next start, which keeps the `taproot.yaml` already written, rather than a deployment whose `taproot.yaml` is missing. A write failure exits 1.
  - **Only for a server run.** `HandleArgs` runs before `flag.Parse`, so it reads the arguments the way the flag package will. It writes nothing when `flag.Parse` will fail or print the help (an undefined flag, `-h`, `-help`, a last flag missing its value), for `--version`, or when a flag other than those a server run may set is on: a login or import, `--tui`, `--discover`, or a plugin's command. It writes nothing either when upstream ignores `--config`: a Postgres, git, or object store, Home mode, or a cloud deploy (`DEPLOY=cloud`).
  - **`.env`.** `main` loads `.env` from the working directory after `HandleArgs`, and `.env` may set `TAPROOT_CONFIG` or the store variables. `HandleArgs` reads `.env` itself, with the process environment winning as it does for `main`, so `taproot.yaml` goes where Setup will look.
  - **No `--config`.** Upstream then reads `config.yaml` from the working directory. When that file does not exist, `HandleArgs` exits 1 with a line that names `--config` and the first run, rather than upstream's bare load error. It writes nothing there, so taproot never drops files into a working directory nobody named. LAN discovery, which reads no config, and the runs above that read their config elsewhere are left alone.
  - **`config.yaml` without `taproot.yaml` still stops startup.** An existing `config.yaml` means a deployment, and a deployment whose `taproot.yaml` went missing (a wrong mount, a bad restore) should stop and say so, not start unclaimed with a setup code in its log. Only a fresh directory gets defaults. A `taproot.yaml` without `config.yaml` (as Nix may seed it) gets `config.yaml` and keeps its `taproot.yaml`.
  - **The setup code.** While the guard is on and no device in `access.devices` has `admin: true`, Setup makes a random 8-character code at each start (`access.Guard.StartClaim`: `crypto/rand` over `ABCDEFGHJKMNPQRSTUVWXYZ23456789`, which leaves out `0`, `O`, `1`, `I`, and `L`, about 40 bits) and logs it at warning level as `setup code XXXX-XXXX` with the dashboard URL (the server's MagicDNS name and listen port). Only a grant the guard can honor counts as Admin: an `admin: true` entry on the server's own node does not, once the node is known, and startup logs a warning naming it. After Setup has armed the claim, any change that leaves no device that can use Admin, such as auto-forget removing the last admin device, a loopback edit, or the server's own node becoming known, makes a new code and logs it the same way, so the server never sits unclaimed without a code until a restart. A logged secret is unusual here; it is the design (plan decision 8, which replaced a `taproot init` command): reading the log needs a shell on the server, which is the trust the first admin needs anyway. The code lives in memory only, works once, and dies with the process. While a device can use Admin, no code is made or logged. Request logs skip `/taproot/**`, so the claim body is never stored.
  - **Claiming.** `POST /taproot/api/v1/claim` with `{code}` (served by the settings module) accepts the code only from a tailnet device other than the server, with a stable ID from whois, in the server's own tailnet: a device whose whois names no node (a sharee's) or a node with another MagicDNS suffix is refused with 403 `claim_own_tailnet_only` before the code is read, so its attempts do not count against the limit. That device gets an `access.devices` entry with `proxy: true` and `admin: true` (replacing its entry if it had one), through the same path as `PUT /settings`: applied to the running guard, written to `taproot.yaml` with its comments kept, and rolled back if the write fails, in which case the code stays valid. Any change that leaves a device with Admin, a claim or a loopback edit, then uses up the code, so later claims get 409 `claimed`, or the guard's `not_admin` once the device list has an admin. The dashboard's connection gate shows the claim screen while the guard's `not_admin` denial carries `claimable: true`.
  - **Guessing.** Wrong codes count per device (stable node ID) against 5 per rolling minute, and against 30 per rolling minute for the whole server. While a device has 5 in its window, its every attempt, the right code included, gets 429 `rate_limited` unchecked; while the server has 30, every device's does. Refused attempts do not extend a window. One device therefore cannot keep another from claiming: a limit for the whole server alone let any device on a shared tailnet lock the owner out indefinitely. At the server-wide 30 a minute, guessing a 40-bit code takes about 27,000 years on average (31^8 codes, half of them tried). Tested with explicit timestamps (`access/claim_test.go`, `access/fixes_test.go`) and a fake clock (`settings/claim_test.go`).
  - **Recovery.** If every admin device is lost, remove the `admin: true` entries from `taproot.yaml` and restart, or remove them on the Access page from loopback: either logs a new code. Loopback stays an admin throughout.
  - The end-to-end flow (missing `--config`, code in the log, a refused loopback and server-node claim, a wrong code, the claim from a tailnet device in a browser, no code after a restart, recovery, and the rate limit) was run against the built server and the demo's fake tailscaled, in a private network namespace with tailnet addresses on its loopback interface.

**No accounts.** When no credential serves a model, upstream answers 400 `unknown provider for model <model>`, which names neither taproot nor the fix, and every new server starts with an empty pool. Upstream builds that message in `sdk/api/handlers/handlers_routing.go`, past every server option, so Setup's third middleware rewrites it rather than an upstream edit. For a `POST`, it holds back a 400 response until the handler returns. When `error.message` starts with upstream's text, it replaces the message with one that names what the pool lacks, read from the auth manager (listed below). Every other response, streams included, passes through as it is written, and the auth manager is read only on that 400 path. Every proxy endpoint returns the error as a JSON body with `error.message` (checked on `/v1/messages`, `/v1/chat/completions`, `/v1/responses`, `/backend-api/codex/responses`, and `/v1/messages/count_tokens`, streamed and not). The middleware runs before upstream's response compression, so a compressed 400 keeps upstream's message. Its writer forwards `FlushError` and `Unwrap` like upstream's own wrappers, so a streaming handler still sees a client that went away and `http.ResponseController` still reaches the connection.

- No credential at all: `no accounts configured: sign in to an account on the taproot dashboard's Accounts page, then retry model <model>`.
- Every credential disabled: `every account is disabled: enable one on the taproot dashboard's Accounts page, then retry model <model>`.
- Otherwise no enabled credential serves the model, as when a pool holds only Codex accounts and a client asks for a Claude model: `no enabled Claude account serves model <model>: add or enable one on the taproot dashboard's Accounts page`, or Codex. The provider comes from the model name's `claude-` or `gpt-` prefix or from upstream's static catalog, because clients send aliases such as `claude-sonnet-4-5` that the catalog lists only with a date. A model of neither provider gets `no enabled account serves model <model>: check the model name, or add an account that serves it on the taproot dashboard's Accounts page`.

Data lives in `<data-dir>` (default `taproot/` beside `config.yaml`):

- `taproot.db`, SQLite in WAL mode
- `request-logs/`
- `backups/`

Each module owns its tables and registers its current schema with `store.Register`, so no shared schema file exists. The code holds no migrations:

- `store.Open` applies every module's idempotent SQL (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`) in module order, in one transaction. Then each module's seed runs in the same transaction, on every Open, and is told whether that Open created the database. A seed never overwrites or restores a row a user edited or deleted; ingest's price seed is versioned for that (see Pricing).
- A schema change in code may only add tables, indexes, or nullable or defaulted columns. A change to a table the deployed database already has is applied to that database by hand. `Open` refuses to start when an existing table lacks a declared column, and names the table and columns. A restore checks the backup's database the same way and refuses one from before such a change (409 `incompatible_backup`), so the database is never swapped for one the next start would refuse.
- A derived table, such as a rollup, rebuilds when empty or stale. At startup, before its writer starts and before the API serves, its module refills each derived table that is empty while its source has rows, or whose request count differs from its source's row count, in one transaction, and logs one info line with the duration. Rows go in primary-key order, and a table that was empty skips the per-row read of a stored row: rebuilding all four tables from 1M events took 26.5 s before that and 12 s after (median of 5 runs). The server does not listen during a rebuild. This covers a release that adds a derived table to a database with history, and a restore of a backup from before the table existed. Data for a derived table goes in a new table, never in new columns of an existing one, because an existing table is never empty and never rebuilds. The count check covers a rollback: the previous release writes events without maintaining the table, so the next start of this release finds the counts apart and rebuilds it.
- `schema_migrations`, from releases that ran migrations, is never read, written, or dropped, so the previous release can still start on the database. That holds only for a database a migrating release created; that release cannot start on one this code created fresh.

### Access

- **Per-device permissions.** Every tailnet device has 2 permissions. **Proxy** sends model requests (the proxy surface). **Admin** opens the dashboard and the management API (the admin surface). `access.devices` in `taproot.yaml` lists the devices that have at least one, as `{id, name, label, proxy, admin}`. A device that is not listed has neither, so a device that joins the tailnet starts with nothing.
  - **Stable IDs only.** A grant attaches to the device's Tailscale stable node ID (`Node.StableID` in whois, `ID` in `tailscale status --json`). Tailscale never reuses one, so a removed device stays out, and a device that takes an old device's name gets nothing. `name` is the device's Tailscale name for people reading the file; it grants nothing, and taproot refreshes it from the tailnet. `label` is optional and the owner's own name for the device (at most 64 characters, trimmed, no control or format characters such as bidi overrides and zero-width characters). It grants nothing either, and taproot never changes it: the name refresh and auto-forget only ever remove the whole entry. Tailscale hides the names of a sharee's devices (see "Devices outside the tailnet"), so for them the label is the only name.
  - **Tagged devices** have no user login (whois reports `tagged-devices`). They are granted by ID like any other device; login-based allowing never could admit them.
  - **Why per device, not per login.** An owner's other servers and routers resolve to the same login, so a login allowlist admitted every process, compromised container, or SSRF on them (security recheck F1), and a second list of admin nodes was needed on top. Colton found the two lists confusing on a real deployment (plan decision 1, 2026-11-08); one list of devices with 2 switches replaces both.
  - **No migration.** `access.allow-logins`, `access.admin-nodes`, and `access.trusted-cidrs` stop startup with a message that names their replacement (`access.RemovedKey`, checked in `taproot.LoadConfig` before the strict decode). An existing file is converted by hand.
  - **Starting with no devices** is allowed: only loopback is then an admin, startup logs a warning, and the server is unclaimed, so it logs a setup code that makes the first tailnet device to enter it an admin (see "First run"). The tailscaled check below still applies, so a fresh install needs the socket mounted or `access.enabled: false`. (Before, an enabled guard refused to start without `allow-logins`.)
- **Identifying callers.** For every request, the guard resolves the caller from its source IP:
  - Loopback addresses are admins with Proxy; `access.addresses` have Proxy only, with the limits in "Security model".
  - Tailnet addresses (`100.64.0.0/10`, `fd7a:115c:a1e0::/48`) are resolved with tailscaled's LocalAPI `whois` over its unix socket (default `/var/run/tailscale/tailscaled.sock`; a container mounts the host's folder, see "Install examples"). The answer is cached for one minute; the decision is not, so a saved switch applies to the next request.
  - A websocket is one request, which the guard admits once, and Codex sessions on one last hours. Upstream re-authenticates each Responses-websocket turn through its access manager, but taproot registers no provider there, so that check allows every turn, and established connections get no timeouts. So the guard tracks every connection a device or an `access.addresses` caller hijacks (`access/sockets.go`, through a wrapper around gin's writer on upgrade requests) until the connection closes, and `SetGrants` closes each one whose caller lost the permission it was admitted with: Proxy on the proxy surface, Admin on the admin surface, or a covering address. That covers a save, auto-forget, and a rollback alike; a change that keeps the permission leaves the connection open. Tracking ends when the handler closes the connection, not when the request returns, because `/v1/ws` returns right after the upgrade and serves the session from another goroutine. A connection hijacked after a revoking change is closed as it is tracked. Taproot does not register an access provider instead, because upstream's middleware asks the same manager on every proxy request: a provider that answered would set the request's API key principal and access provider, which usage records keep, and one that declined would turn the manager's empty-list allow into 401 for every request.
  - The server's own node always has Proxy and never Admin, whether or not it is listed (see "Security model").
  - Every other tailnet device gets what its `access.devices` entry says, except that a device with Admin also reads the model list without Proxy (see "Security model"). A whois without a stable ID admits nothing.
  - A tailnet device is *outside* the server's tailnet when whois names no node for it (`Node.Name` empty, as for a sharee's device) or a node whose MagicDNS suffix differs from the server's. Outside-ness changes nothing about admission or about which permissions a device may be given; it limits only who may claim (see "Devices outside the tailnet").
  - Everything else gets a 403, including whois failures. `/healthz` is exempt.
- **Why source IPs and not `tailscale serve` headers.** Source IPs work for the proxy port, so client configs stay as they are, and tailnet source addresses can't be forged.
- **Keyless management.** At setup, the guard puts a random secret in `MANAGEMENT_PASSWORD`, unless an operator already set one. Upstream's management handler reads that at construction. For admitted callers, the guard injects `Authorization: Bearer <secret>` on `/v0/management/*`, `/v8/management/*`, and plugin resource routes. The secret never leaves the process. A `secret-key` in `config.yaml` keeps working for scripts.
- **Proxy keys.** Proxy API keys (`access.api-keys`) are irrelevant once the guard admits callers by identity. They stay empty.
- **tailscaled at startup.** An enabled guard without tailscaled refuses every tailnet caller, so Setup fails when the socket does not exist or refuses a connection, and the error names the socket and how to mount its folder. It checks the connection only, within the LocalAPI's 3 s limit: a tailscaled that answers with an error, such as while it logs in, does not stop startup, and the guard keeps retrying.
- **tailscaled while running.** A container that holds a stale socket after tailscaled restarts refuses every tailnet device, admins included, while `/healthz` stays ok (seen on a server when an auto-update took tailscaled from 1.104.2 to 1.104.5; see "Install examples"). `MonitorTailscaled` (`access/tailscaled_monitor.go`) reads LocalAPI status every 30 s with the client's 3 s timeout. When the reads have failed for 2 minutes, whether or not one succeeded before, it logs one error naming the socket, the cause (a missing socket or a refused connection points at a stale mount after a tailscaled restart, so it says to restart taproot; any other error says to check tailscaled), and the troubleshooting entry, and queues one alert (see "Alerts"). The first read that succeeds after that logs and queues one recovery. A failure shorter than 2 minutes logs one warning, and one info line when it ends, and sends nothing, since a restart of tailscaled itself takes seconds. `/healthz` does not change, because `taproot-update` health-checks it after an update, and taproot never exits for it.
- **Development.** Without tailscaled, as on Windows, set `access.enabled: false`, which leaves the admin surface loopback-only. The demo (`internal/taproot/demo/run.sh`) keeps the guard on and serves a fake tailscaled (`demo/tailnet.go`) that answers whois and status for a synthetic tailnet, so its server starts and the Access page has devices to show.
- **Guard disabled.** With `access.enabled: false`, the proxy surface admits every caller with no Host or browser checks, and the admin surface still answers loopback only (launch audit B2: before this, a remote caller read settings and created and downloaded a backup). Loopback admin requests still get the browser checks (Host, Origin, `Sec-Fetch-Site`, and `X-Taproot-Request` on state-changing GETs), because a browser on the same host connects from loopback too (review finding 2: without them, any page could create, download, or restore a backup). No key is injected, so management auth is upstream's. The startup warning names both surfaces. The Access page lists the configured grants and refuses edits (409 `access_disabled`).
- `GET /taproot/api/v1/me` returns `{login, displayName, node, nodeId, via: "loopback"|"tailnet"|"cidr", proxy, admin}`. It is on the admin surface, so only admins reach it.
- **Denials the dashboard and clients can explain.** The guard's 403 is `{error: {code, message}}`. The code is `forbidden`, except in the cases below. In the first two the caller is a tailnet device other than the server, on a request that passed the browser checks, so the body tells it only its own name, login, and ID:
  - `no_proxy`, with `node`, `nodeId`, and `login`, for a proxy request from a device without Proxy. Command-line clients show only the message, and Claude Code prints it after its own advice (`Failed to authenticate. API Error: 403 <message>` in print mode, `Please run /login · API Error: 403 <message>` interactively, measured), which is wrong here. The message is therefore `This device needs approval on taproot. Don't run /login. Open http://<host> on this device to name it, or ask the server's admin. (<name>, <login>, ID <id>)`, where `<host>` is the request's `Host` (it passed the Host check, so it is one of the server's names; `https` when the request came over TLS) and `<name>` is `unnamed device` when whois names no node. A device whose grant has Admin needs no approval, so its message is `This device has Admin but not Proxy on taproot. Don't run /login. Open http://<host> and turn on Proxy for this device on the Access page. (<name>, <login>, ID <id>)`. The status stays 403 and the code `no_proxy`.
  - `not_admin`, with `node`, `nodeId`, `login`, `proxy`, and `requested`, for an admin request from a device without Admin. `requested` says whether the device has an open access request, read before this refusal is recorded, so a first visit shows the connection gate's request form and a later one its sent state. While the server is unclaimed, every such body has `unclaimed: true`, and the body of a device in the server's own tailnet also has `claimable: true`, so the gate shows the setup code form instead. A device outside the tailnet cannot claim, so its body never has `claimable`; the gate tells it that the server has no admin yet and must be claimed from a device in its own tailnet, rather than offering a request no admin could allow.
  - `request_header_required` for a state-changing GET without `X-Taproot-Request: 1` (see "Security model").
  - `guard_disabled` for an admin request from a non-loopback caller while `access.enabled` is false (see "Guard disabled").
  - `server_node` for an admin request from the server's own node, which never gets Admin, so a browser on the server is told to use another device rather than that it is off the tailnet.
  - `server_node_unknown` for an admin request from a device whose grant has Admin while the guard withholds it: the server's own node was never read, or the caller's address is still the server's in tailscaled's status. It says to try again in a few seconds.
  - `unknown_host`, with `host`, for a `Host` the server does not answer to. A request whose `Accept` includes `text/html`, as a browser's navigation does, gets a short HTML page instead, which names the refused host and says to use the server's Tailscale name or address, or to add the name under `access.extra-hosts` and restart. It names none of the server's own names or addresses, because a page that reached the server through DNS rebinding reads that response; while the server's names cannot be read from tailscaled, it says so.
- **The Access page.** `GET /taproot/api/v1/access/devices` reads tailscaled's `GET /localapi/v0/status?peers=true` and joins it with `access.devices`: each device's name (its MagicDNS name without the server's tailnet suffix, so a device from another tailnet keeps its full name, as usage history names it; else its host name), label, MagicDNS name, stable ID, owner login and display name (empty for a tagged device), tags, OS, created time, whether it is outside the tailnet, `online`, `lastSeen` (left out while unknown), its Tailscale IPs (`addresses`, IPv4 first), and both permissions. A sharee's device has an empty name (see below), and its 1973 placeholder join date is dropped. The server's own node comes first with Proxy on and Admin off. Granted devices the read does not list follow, with `onTailnet: false`. When the read fails, `tailnetError` says why and only granted devices are listed. 12 peers came to 17.6 KB (measured). The LocalAPI client reads at most 16 MiB of the peer list, about 11,000 peers at that density, and 1 MiB of other answers; a longer answer is an error that says so rather than a truncated body. The endpoint only reads; the page saves through `PUT /settings`, which applies the lists to the running guard, then writes `taproot.yaml`, and rolls the guard back if the write fails.
  - **Stale pages.** `GET /access/devices` and `GET /settings` return `version`, a hash of the device and address lists (`Grants.Version`). The save bar sends whole lists with the `version` it loaded, and `PUT /settings` refuses them with 409 `access_changed` when the lists changed since, so a tab loaded before another admin's save cannot undo it, such as a revoked Admin. The page then reloads and keeps the draft's edits to devices, labels, and addresses that nobody else changed, drops the rest, and says so. Allow sends only its device, as `access: {device}`, which the server merges into the current list, so it needs no version. A `PUT` without `version` is not checked, for scripts. The page counts its loads, ignores every response but the newest, and makes loads in flight stale when it saves, so a response read before a save never replaces the page after it. The header's refresh reloads with the draft kept, and leaving the page with unsaved changes asks first.
  - A `PUT` that takes Admin from the calling device is refused (409 `would_lock_out`), and so is one that gives the server's own node Admin (400 `server_admin`). Loopback callers are admins whatever the lists say. The server's node comes from the guard's own lookup, which reads tailscaled's status when no request has read it yet, so the check holds on a server only loopback has called. While tailscaled cannot be read and the node was never read, a `PUT` that gives Admin to a device that did not have it is refused (503 `server_node_unknown`), since that device could be the server; other saves go through. The setup-code claim reads the node the same way.
  - A device with neither permission is dropped from the list on save, so `access.devices` holds only devices with a permission.
  - The page lists, top to bottom: open requests, each named by the device's label when it has one and marked "wants dashboard" when it asked for Admin, with Allow (a name, prefilled with the device's label, else the name the device gave itself, else its Tailscale name, and saved as the label, so an untouched field keeps the owner's label; Proxy on, and Admin on only when the device already has it) and Deny; Yours (the devices of the viewer's login and of every in-tailnet device with Admin); Servers (tagged devices and this server); a section for each other person with a granted device; one folded line for every other device without access (a sharee's, another person's, or one idle for over 30 days); Removed (granted devices no longer listed); and addresses. Device rows show no online or last-seen line; `online` and `lastSeen` only decide which devices are idle. Allow saves through `PUT /settings`, then closes the request with `POST /access/requests/:nodeId/allow`; the save goes first, so a failed save leaves the request open to try again. When the save succeeds and the close fails, the page says the access was saved but the request is still open, and reloads.
  - Every row whose draft gives the device a permission has a pencil that edits its label in place; the server's row has none. A label is saved only with a permission, so a device with neither has no pencil until a switch is turned on, and a name staged before both switches are turned off is neither shown nor counted as a change, and comes back if a switch is turned on again before the save. Enter or leaving the field stages the name in the draft, and the save bar saves it with the switches; Escape cancels. The page checks it as the server does (trimmed, at most 64 characters, no control or format characters), and a name equal to the Tailscale name, or an empty one, saves no label, so the row shows the Tailscale name. A device without a permission is dropped on save, label and all, as above.
- **Auto-forget.** A granted device whose ID is missing from tailscaled's list across successful reads for 24 hours (`access.ForgetAfter`) is removed from `access.devices`, live and in `taproot.yaml`. The settings module reads the tailnet at start and every 10 minutes, and the Access page's reads count too.
  - A failed read, a read while tailscaled is not `Running`, and a read with no peers never count, so a tailscaled restart or logout can't wipe access. A device that comes back starts its 24 hours over.
  - The first-missing times are in memory only, so a taproot restart starts every device's 24 hours over. That only delays forgetting.
  - The same pass refreshes each entry's `name` from the tailnet, never its `label`, and never to an empty name. Neither change touches a permission of a device still on the tailnet.
  - Tested with a fake clock against the fake tailscaled (`access/roster_test.go`) and through the settings write path (`settings/settings_test.go`).
- **Devices outside the tailnet.** Measured on tailscaled 1.104.2: when the server's node is shared with a person, `status` lists every device of that person, not only those shared back, with `ShareeNode: true`, `HostName` `device-of-shared-to-user`, an empty `DNSName` and `OS`, no tags, `Created` `1973-11-11T00:00:00.1Z`, a real stable `ID`, `Online`, `LastSeen`, and a `UserID` in the user map. whois for one names no node (`Node.Name` empty, `ComputedName` and `Hostinfo.Hostname` the placeholder) but has the stable ID and the person's login. Tailscale hides their names on purpose, but not their Tailscale IPs (`TailscaleIPs`), and the IPs taproot sees match the ones the owner sees in their own admin console and apps (confirmed by an owner). The page therefore names such a device by its label, else `<owner>'s device · <its IPv4>`, else `<owner>'s device · <its IPv6>`, and only for a device without an IP `<owner>'s device ·<4 characters of the ID before CNTRL>`, which the owner has no easy way to match. A request from a device without a label or a name of its own is named the same way, and search matches the IPs. A sharee's device can open connections to the server; a device shared into the tailnet cannot.
- **Access requests.** A refusal becomes a request, so nobody has to find a stable ID to let a device in.
  - Recorded: a `no_proxy` or `not_admin` refusal of a tailnet device with a stable ID upserts its row in `access_requests` (`node_id`, `login`, `owner_name`, `node_name`, `outside`, `first_seen`, `last_seen`, `count`, `client`, `name_hint`, `dismissed_at`, `asked`, `allowed_at`). `asked` is what the device was refused, `proxy` or `admin`, keeping the wider one seen, since Admin implies Proxy; the gate's self-request asks for `admin`. Never for loopback, `access.addresses`, the server's own node, callers with no identity, a device that has the permission it was refused, or a device whose grant has Admin, even while the guard withholds Admin because the server's own node is unknown. An admin can turn on what it lacks itself on the Access page, so a request would only announce the owner to themselves: before this, an owner's phone with Admin and no Proxy raised a request and an "Access requested" alert by opening the dashboard, whose home page read `/v1/models` (measured on a production server, 2026-11-09). `client` is a word for the User-Agent (`Claude Code`, `Codex`, `curl`, `Browser`, else empty). Writes are spaced one a minute per device, in memory; the refusals in between are counted and added on the next write, and the write runs on the refused request, which then answers.
  - Self-request: `POST /taproot/api/v1/access/request` with an optional `{name}` lets a device without Admin ask from its browser and name itself (a device whose grant has Admin gets 409 `has_access`) (`name_hint`, trimmed, at most 64 characters, no control or format characters). It grants nothing. It is limited to 10 per device per rolling hour (429 with `Retry-After`).
  - A request is open while neither `allowed_at` nor `dismissed_at` is set. It opens when the device has no row. Opening or reopening queues one Discord message (see "Alerts"); an update of an open request queues nothing.
  - Allow is a decision, like Deny. A save through `PUT /settings` that gives a device a permission it did not have sets its request's `allowed_at`, and the Allow form then calls `POST /access/requests/:nodeId/allow`, which sets it even when the save gave nothing new, as for a Proxy-only device that opened the dashboard and was allowed with the defaults. A later refusal of an allowed request only updates `last_seen`, `count`, and `asked`; it neither reopens it nor alerts, so a device that got less than it asked for is not announced on every visit. The device's own request from the gate reopens it, with `first_seen` and `count` reset, the new name, and one alert.
  - Deny (`dismissed_at`) is reopened by the next refusal or self-request, as a new request.
  - The page hides the request of a device that already has both permissions.
  - Pruned by the settings module's tailnet sweep: the row of a device that successful reads with peers have not listed for 24 hours (`access.ForgetAfter`, tracked in memory as for granted devices), and an allowed or denied row whose decision and last refusal are both over 30 days old. Open rows of listed devices stay. Tested with a fake clock (`access/requests_test.go`).
  - Every read-then-write of `access_requests` (recording a refusal or a self-request, and pruning) runs in a `BEGIN IMMEDIATE` transaction (`store.WithImmediateTx`), and Allow and Deny are single statements. The database is shared in WAL mode, and a deferred transaction that reads and then writes fails with `SQLITE_BUSY` when another writer commits first, which `busy_timeout` does not retry: 159 to 192 of 200 concurrent refusals of 10 devices failed that way (measured, `TestRequestsConcurrentWriters`), and none fail now.

### Security model

The guard splits the server into two surfaces. The package comment in `internal/taproot/access/access.go` is the code-side copy of this section.

- **Admin surface.** Everything that reads or changes credentials, settings, backups, or plugins:
  - the dashboard (`GET`/`HEAD /` and its chunks under `/assets/`), except that the static page and chunks load for every identified caller (see the note under the table)
  - `/v0/management/**` and `/v8/management/**`, including the plugin management routes upstream serves from `NoRoute`
  - `/taproot/**`
  - plugin pages and assets under `/v0/resource/plugins/**` (the dashboard frames them same-origin)
  - the OAuth callbacks on the main port (`/anthropic/callback`, `/codex/callback`, `/antigravity/callback`, `/callback`, `/devin/callback`), which write the code for a pending login
  - `/v1/ws`, which registers a websocket client as an AI Studio credential
- **Proxy surface.** Everything else, such as `/v1/messages`, `/v1/responses`, `/backend-api/codex/**`, and `/v1/models`. A device with Admin reads `GET /v1/models` without Proxy (see the note under the table); every other proxy request needs Proxy.
- **Who reaches what.**

  | Caller | Proxy | Admin |
  |---|---|---|
  | Loopback (inside the container, or local development) | yes | yes |
  | `access.addresses` | yes | no |
  | The server's own node (`server`, `100.64.0.1`), listed or not | yes | no |
  | A device with `proxy: true` in `access.devices` | yes | |
  | A device with `admin: true` in `access.devices` | only `GET /v1/models` | yes |
  | Any other tailnet device, including a new one | no | no (only `POST /taproot/api/v1/access/request`, and `POST /taproot/api/v1/claim` while unclaimed) |
  | Anyone else, including whois failures | no | no |

  - **The dashboard page is open to every identified caller.** `GET`/`HEAD /` returns the static build, which holds no data, and `GET`/`HEAD /assets/*` its chunks, which follow the page: the same callers reach both, in both guard modes, so with `access.enabled: false` they stay loopback-only like the page. A tailnet device without Admin, including one with no permission at all, can therefore load it, and the connection gate lets it ask for access and name itself: "This device doesn't have access yet." for a device with no permission, "This device can use the proxy but not the dashboard." with "Request dashboard access" for one with Proxy, and the sent state, with Check again, while its request is open. While the server is unclaimed, a device in the server's tailnet gets the setup code form instead, and any other device is told the server is not set up yet. A caller with no identity (not loopback, not in `access.addresses`, and no whois answer with a stable ID) gets nothing, not even the page. Every request for data is still admin-only.

  - **Admin reads the model list.** The dashboard's home and System pages list models from `GET /v1/models`, so a device with Admin and no Proxy reaches that exact path with `GET`, and nothing else on the proxy surface: `/v1/models/<id>`, `/v1beta/models`, and `POST /v1/models` still need Proxy. The handler (`unifiedModelsHandler` in `internal/api/server_routes.go`, then `OpenAIModels` or `ClaudeModels`) answers from the in-memory model registry (`registry.GetGlobalRegistry()`), with no upstream call and no quota; its Home branches never run, since taproot refuses Home mode. The list names no credential or account, only the models an admin already sees in the dashboard. The exception follows the guard's Admin, not the grant alone, so it closes while the server's own node is unknown.
  - **The server's own node is proxy-only.** Under rootless Podman, containers and local users on the server host reach the published `100.64.0.1:8317` with that source address (measured through pasta). Agents running on the server need the proxy, so the node keeps it without an entry in `access.devices`, but none of those processes gets credentials or settings. An entry for it with `admin: true` is ignored, and `PUT /settings` refuses one. A tagged server node has no user login, which is why the grant never depended on one. Every process on the host reaches the proxy through its node, and no more. That includes anything on the host that forwards to the Tailscale publish, such as `tailscale serve` or `funnel` pointed at port 8317, so do not point those at taproot. When whois answers, the event records the login it reports.
  - **The server's own node comes from tailscaled.** The guard reads `Self` from `GET /localapi/v0/status?peers=false`. A caller is the server when its whois `Node.StableID` equals `Self.ID`; only when whois fails or has no node ID does an address in `Self.TailscaleIPs` decide, because the status list can be a refresh behind an address the console reassigned. An address still in that list never gets admin access. The guard refreshes `Self` every cache TTL and keeps the last known node when a refresh fails. When a refresh finds another node ID or tailnet suffix, as after `tailscale switch`, it clears the whois cache, whose addresses may now belong to other devices. `cache-ttl` is at most 10 minutes, because an address that changes hands keeps its previous device's identity for up to that long; a larger value stops startup. Until the first read succeeds, tailnet callers get no admin access, only local Host names pass the Host check, the server's own node is just a device and needs its own entry for Proxy, and a warning is logged.
  - **`access.addresses` are proxy-only.** They hold host-local addresses that every local process shares. Under rootless Podman, a host-local client that uses a `127.0.1.1:8317` publish arrives as the host's LAN address, such as `192.168.0.88` (measured through pasta). If such a client needs the proxy, add `192.168.0.88/32`, never `192.168.0.0/24`, which would admit the whole LAN. A bare address is read as a single-address prefix, and an IPv4-mapped IPv6 entry such as `::ffff:192.0.2.20` as the IPv4 prefix it means, because admission unmaps the caller's address. Local clients can also use the Tailscale publish, `100.64.0.1:8317`, instead.
  - An entry that overlaps `100.64.0.0/10` or `fd7a:115c:a1e0::/48`, such as `100.64.0.0/10` itself, a tailnet `/32`, or `0.0.0.0/0`, is refused at startup and on save (400 `invalid_access`), and the Access page refuses it before saving. Admission matches addresses before whois, so such an entry would hide the identity of every device it covers: each would get Proxy without a grant, and an admin device would lose Admin, with only loopback left to undo the save. Because of that refusal, no address change can lock out a tailnet caller, so `would_lock_out` checks devices only.
  - **The claim route is the one exception, and only while unclaimed.** While no device has Admin and a setup code is waiting, the guard lets a tailnet device other than the server, identified by whois with a stable ID, through to `POST /taproot/api/v1/claim` and nothing else on the admin surface, after the same Host, Origin, and `Sec-Fetch-Site` checks as every request. The handler then refuses loopback, `access.addresses`, and the server's own node (403 `claim_tailnet_only`) before reading the code, so their attempts do not count against the limit; the guard already refuses the latter two. Without the code the route reveals only that the server is unclaimed, which the `not_admin` denial's `unclaimed` and `claimable` say too. The moment a device has Admin, the route closes for every caller without Admin. A cross-site page cannot claim for a visitor either: it would need the code, and the Origin check refuses its `POST`.
  - **The access request route is the other exception.** A tailnet device other than the server, without Admin and identified by whois with a stable ID, reaches `POST /taproot/api/v1/access/request` and nothing else on the admin surface, after the Host, Origin, and `Sec-Fetch-Site` checks and with `X-Taproot-Request: 1`, which a cross-site page cannot send. The handler refuses loopback (403 `request_tailnet_only`); the guard already refuses `access.addresses`, the server's own node, and callers with no identity. It records a request and grants nothing, so the worst a device can do is announce itself, at most 10 times an hour.
  - **Only a device in the server's own tailnet may claim an unclaimed server.** A device shared in from another tailnet, or a sharee's device, is refused (403 `claim_own_tailnet_only`), so the setup code alone cannot hand the server to another account. Once claimed, an admin may give such a device Admin with its switch: its row shows its Tailscale IP, which its owner sees too, so it can be told apart from the admin's own devices.
  - **Admin is deny-by-default.** With no device holding Admin, no tailnet caller is an admin and only loopback is, and startup logs a warning. An owner's other server nodes and routers resolve to the same login, so a grant by login would hand any process, compromised container, or SSRF on them the owner's tokens and settings (security recheck F1). A grant by stable ID covers exactly one device.
    - Names grant nothing. A device's MagicDNS name derives from its hostname unless it was set in the admin console, and names are unique only while held, so after a device is deleted or renamed another node can claim its name with `tailscale set --hostname` (security re-review F1). The previous `admin-nodes` list matched names too; a stable ID is never reused, so per-ID grants do not have this gap.
    - The Access page edits the grants. A change that takes Admin from the caller's own device is refused; loopback callers are exempt.
  - **Never publish the port on host loopback.** Publishing `127.0.0.1:8317` could make pasta deliver host connections with a loopback source (inferred from pasta's splice path, not measured), which would make every host process an admin. Publish on the host's Tailscale address (and `127.0.1.1` if host-local clients need it) instead.
- **Browser hardening.** The admin surface is keyless for admitted callers, so any page the admin visits could otherwise use the admin's tailnet address. Upstream answers every request with `Access-Control-Allow-Origin: *` and its websocket upgraders accept any origin. The guard runs before upstream's CORS middleware on both surfaces, and its 403 carries no CORS headers. It rejects:
  - a `Host` that is not one of the server's names: `localhost`, any loopback address, the server's tailnet addresses, its MagicDNS name with and without the tailnet suffix (`server`, `server.tailnet-0000.ts.net`, with or without a trailing dot), and `extra-hosts`, each with any port. This stops DNS rebinding.
  - an `Origin` whose host and port differ from the request's `Host`, or that is not http or https (including `null`). This covers CORS preflights, websocket upgrades, and every cross-site request a browser sends with a method other than `GET` or `HEAD`, including form posts and no-cors `POST`s.
  - `Sec-Fetch-Site: cross-site` or `same-site`, except top-level `GET` navigations (`Sec-Fetch-Mode: navigate`, `Sec-Fetch-Dest: document`) to the dashboard and the OAuth callbacks, including `/v0/management/oauth-callback` and `/v8/management/oauth/callback`, where plugin providers redirect a browser on the server host (upstream builds those redirect URIs on `127.0.0.1`, and browsers send `Sec-Fetch-*` to loopback). Following a link to the dashboard or a provider redirect still works. **This layer only works over https or to loopback.** Browsers send `Sec-Fetch-*` only to potentially trustworthy targets, and taproot is used at a plain-http tailnet name such as `http://server:8317`, so there a cross-site no-cors `GET` or `<img>` arrives with no `Origin` and no `Sec-Fetch-*` (measured in Chrome 156 by the security recheck, F3). The other site cannot read the response, but the handler runs.
  - a state-changing `GET` without `X-Taproot-Request: 1`, from any caller, loopback included. That covers the gap above: a cross-site page cannot add a custom header without a CORS preflight, and the guard rejects the preflight's `Origin`. The routes are `/v0/management/usage-queue` and `/v8/management/observability/usage/queue` (reading drains the queue), every `/v0/management/*-auth-url` and `/v8/management/oauth/auth-url` (each starts a pending OAuth login), and `/v0/management/get-auth-status` and `/v8/management/oauth/status` (which mark a finished login adopted). The outbound fetches are on the list too: the plugin store (`/v0/management/plugin-store`, `/v8/management/plugins/store`), the latest release (`/v0/management/latest-version`, `/v8/management/server/latest-version`), and plugin quota probes (`/management/plugins/:id/quota`), which use stored credentials.
    - Plugin management `GET`s are assumed read-only. Upstream lets a plugin register any `GET` handler, so a plugin that acts on a `GET` could be triggered cross-site. Claude Keep Rolling's only action, a manual ping, is a `POST`.
    - Gin's trailing-slash redirects run before any middleware, so a stranger can learn which routes exist from a `301`/`307` `Location`. No data comes back, and the followed request is guarded.
    - The dashboard's management and taproot clients always send the header.
    - Read-only `GET`s need no header, so plugin pages such as Claude Keep Rolling's status page keep working. A cross-site `GET` there cannot read the response.
    - The `GET` OAuth callbacks are not on the list. Providers reach them by navigation, and they act only on a pending login whose random state the caller must know.
    - Loopback needs the header too (review finding 9), so the check does not depend on the browser sending `Sec-Fetch-*` to loopback targets. Upstream's TUI client calls these routes, so `internal/tui/client.go` sends the header on every request: one line in `doRequest`, an upstream edit for this reason.
  - The proxy surface gets the same checks, so a web page cannot spend quota either.
- **Command-line clients are unaffected.** Claude Code 2.1.316 and Codex 0.159.3 (HTTP and websocket) send no `Origin` or `Sec-Fetch-*` headers, and `Host` is the base URL's authority (measured against a header-capture server on 2026-11-02). Over the 3,000 most recent request logs of a production deployment, no request carried `Origin`, `Sec-Fetch-Site`, or `Referer`.
- **Framing.** The dashboard response sets `X-Frame-Options: DENY` and `Content-Security-Policy: frame-ancestors 'none'`. Other admin responses get `X-Frame-Options: SAMEORIGIN`, so only the dashboard can frame plugin pages.
- **Upstream control panel.** The guard answers `/management.html` with 404 for every caller, so upstream's auto-downloaded panel never runs same-origin with keyless management, whatever `remote-management.disable-control-panel` says.
- **Accepted:** a plugin page under `/v0/resource/plugins/**` runs same-origin with keyless management. Plugins already run in the server process with full access, so this adds nothing.

### Ingest

- **Usage events.** Ingest registers a `usage.Plugin` with `usage.RegisterNamedPlugin("taproot", ...)`. Each `usage.Record` becomes a `usage_events` row with these fields:
  - ids: request, trace, session, parent session
  - provider, model, alias, auth index and id
  - stream flag, failed flag, status code
  - latency, time to first token
  - tokens: input, output, reasoning, cache read, cache creation, and the 5m and 1h cache-creation splits
  - service tier
  - device: the caller the access guard admitted (`node:<StableID>` for a tailnet node, `local` for loopback and the server's own node, `cidr:<address>` for an `access.addresses` caller), with its name, login, and how it was reached. Events recorded before device attribution have no device.
  - **Plugins.** A plugin's in-process model request (`host.model.execute`) has no HTTP caller. It gets the device `plugin:<plugin ID>`, named after the plugin's metadata name (for example "Claude Keep Rolling"), with via `plugin`. When the host marks a plugin call without its ID, the device is `plugins`, "In-process plugins". Limits: upstream's non-streaming `host.model.execute` does not check that a callback ID belongs to the calling plugin (the streaming path does), so a plugin can attribute its usage to another plugin or to that plugin's client; native plugins already run in-process with full access, so this is accepted. With the guard disabled, a client request a plugin forwards is credited to the plugin. Tests build the loaders' context by hand; if upstream stops tagging it, plugin usage falls back to an empty device without a failing test.
    - The admitted HTTP caller wins when the guard knows the record's request ID. A plugin that executes a client's request through the host, such as `claude-web-search-router`'s fallback, carries that request's ID, and the usage is the client's. Upstream assigns request IDs only under `/v1`, `/v1beta`, `/openai/v1`, and `/backend-api/codex`, so a plugin's timer or a management or plugin-page action never has one.
    - The device is resolved when the record is queued, not when it is written: the guard keeps a request's device for ten minutes after the request, and a flush that keeps failing can come later.
    - Stored device IDs are never rewritten. Claude Keep Rolling pings recorded before plugin attribution keep an empty device. The dashboard labels that group "No caller recorded", which is true of every empty-device event. Mapping them to the plugin at read time would rest on their shape (Haiku, 100 input and 1 output tokens, no request ID), and other callers without a request ID, such as routes outside those prefixes, share the missing ID.
  - **Names at read time.** For `access.addresses` devices, the devices and events APIs ask the guard for the current name, so imported history shows it too; plugin devices keep the name stored when their usage was recorded. Read-time naming also renames past rows if an address later changes hands. The request path stores the bare address and never reads the interfaces. An `access.addresses` device whose address is one of the server's own interface addresses is named `<server> (via <address>)`, such as "server (via 192.168.0.88)": only a process on the server host connects from that address (under rootless Podman, a `127.0.1.1` publish arrives through pasta as the LAN address). The server cannot see which publish was used, so the name says what it knows: the host and the address. The address also separates the row from "server (local)" and matches the `access.addresses` entry. The guard reads the interfaces with `net.InterfaceAddrs` at most once a minute and keeps the last list when a read fails. The device ID stays `cidr:<address>` and access stays proxy-only; the own-address check names devices and never admits.
- **Derived usage tables.** The writer folds each flush of new events into these tables in the same transaction, so the dashboard's usage reads do not scan every event in a range. Each rebuilds from `usage_events` when empty or when its request count differs from the events (see Architecture); `usage_sessions` follows `usage_session_hourly`. Hours are UTC hours since the epoch (`ts / 3600000`). The rollups carry the token sums, request and failure counts, and log-bucketed latency and TTFT histograms. Summaries read whole hours from a rollup and the partial hours at a range's edges from raw events. Daily buckets in a zone whose offset is not a whole number of hours, such as `Asia/Kolkata`, read each hour that a local midnight splits from raw events too, and the rest from the rollup, instead of scanning every event in range (measured on 1M events over 30 days in `Asia/Kolkata`: 3.7 s before, 0.2 s after, median of 5 runs).
  - `usage_rollup_hourly(hour, provider, auth_index, model)`: summaries grouped by model, account, or provider.
  - `usage_device_hourly(hour, device_id, model, main)`: summaries grouped by device and the devices tab. `main` marks Claude main-conversation requests, and `split_requests` counts requests with a known 5m/1h cache-write split. It replaces `usage_rollup_device_hourly`, which had no histograms. The code no longer declares or writes that table, and a deployed database keeps it until it is dropped by hand.
  - `usage_session_hourly(hour, session_id, model)`: summaries grouped by session. Events without a session have the empty `session_id`.
  - `usage_sessions(session_id)` with `first_ts` and `last_ts`, indexed on `(last_ts, session_id)`: the sessions list. A session whose last request is before a range's end has its last request in range at `last_ts`. Only sessions that span the end are measured from their events.
- **Quota observations from headers.** Each record's `ResponseHeaders` supplies quota observations:
  - Anthropic: `anthropic-ratelimit-unified-{5h,7d,...}-{utilization,reset,status}`
  - Codex: the `x-codex-*` primary and secondary used-percent, window, and reset headers
  - A row goes to `quota_observations(auth_index, provider, window, utilization, resets_at, status, observed_at)` when a value changes, or when 5 minutes have passed since the last row for that account and window.
- **Polling idle accounts.** A poller covers accounts with no recent traffic. It reads the same usage endpoints the dashboard's quota adapters read (`api.anthropic.com/api/oauth/usage`, `chatgpt.com/backend-api/wham/usage`), through the auth manager's credentials. The default interval is 15 minutes, it is configurable, and `0` disables it. Its requests, and the manual refresh's, leave the way the credential's proxied requests do (`internal/taproot/egress`): through the credential's `proxy-url`, else `requests.proxy-url` from `config.yaml` (read on each request, so a reload applies), else directly. A configured proxy that does not parse stops the request with a warning instead of sending the token directly.
- **Claude windows.** The Claude usage response lists its limits in `limits[]`, and the poller reads that first: `session` is `five_hour`, `weekly_all` is `seven_day`, a `weekly_scoped` item whose model display name is Fable or starts with "Fable " (Claude Code's allowlist: "Fable", "Fable 5", "Fable 5.1") is `seven_day_fable`, and any other scoped model is `seven_day_<model slug>`. A top-level window key adds only a window the array did not report; `iguana_necktie` and `seven_day_overage_included`, Anthropic's own name for the Fable limit, both map to `seven_day_fable`, as the header claim `7d_oi` does. Anthropic now leaves the legacy keys null, so before this the Fable limit was never recorded. The Fable window is model-scoped (`accountWide: false`): at its cap, Fable runs on usage credits and the other models keep working. Some accounts have no 5-hour limit: their `limits[]` has no `session` item and `five_hour` is null. An account with the limit keeps its `session` item while no session is open (`is_active: false`, a `resets_at` that may have passed). So a non-empty `limits[]` without a `session` item means the account has no 5-hour limit, whatever `five_hour` says. The poller then records a `five_hour` row with status `no_limit`, utilization 0, and no reset. It replaces any older reading as the window's latest, and the latest-reading reads (`/quota/current`, `LatestQuota`, and the refresh response) leave a window whose latest row is `no_limit` out, so pools, `/status`, alerts at start, and the Accounts page see no 5-hour window for the account. Quota subscribers (alerts, routing) receive the row as a 0% reading, which ends an older limit hit. History keeps the rows as 0% points. This adds no column: `status` already holds free text. Without `limits[]` (older responses, or an empty array), `five_hour` null means no session is open; the poller then records an empty `five_hour` window with no reset, so a reading from a session that ended days ago stops showing as current. On the live server, an account without the limit had weekly header readings but no 5-hour header readings, so no header reading brings the window back. Fable's share of the weekly limit (`weekly_scoped_shares`) is not stored: the Accounts page reads it live (see "Dashboard scope").
- **Manual refresh.** `POST /quota/refresh` polls one account's usage endpoint on request, at most once per 30 seconds per account. Refreshed observations are always stored, so the account's `observedAt` moves even when nothing changed.
- **Development overrides.** `TAPROOT_DEV_CLAUDE_USAGE_URL` and `TAPROOT_DEV_CODEX_USAGE_URL` replace the two usage endpoints, so a local dashboard can exercise quota refresh against a fake server. Only loopback URLs (`127.0.0.1`, `localhost`, `::1`) are accepted; any other value is ignored with a warning, so a stray variable cannot send tokens off the machine.
- **Observation times.** A poll or refresh stamps its observations when the response arrives, so a slow endpoint does not age the later accounts of a poll round, and a Codex reset given in relative seconds counts from the response. An observation older than the window's stored one is dropped, because headers arrive out of order. The exception is a stored observation more than a minute ahead of the clock: it was written while the clock ran ahead, so newer readings replace it rather than wait for the clock to catch up, both in what is stored and in the latest reading that `/quota/current`, `LatestQuota`, and the poller read. The stale row is still stored, so when the clock reaches it, it is again the newest reading until the next one replaces it: at most one poll interval for an idle account.
- **Latest readings.** `/quota/current`, `LatestQuota` (which seeds alerts at start), and the poller's idle check share one loose index scan over `quota_observations_key`, so they cost one seek per account window rather than a scan of the history (measured on 4.2M rows: `LatestQuota` took 8.7 s before and 1 ms after, median of 5 runs).
- **Account labels.** `accounts(auth_index, provider, label, email, plan, first_seen, last_seen, disabled)` is refreshed from the auth manager. It gives imported and historical rows labels. An account the manager no longer lists is marked removed, the last one included: the server attaches the manager after it loaded the stored credentials, so an attached manager's empty list means none are left. A credential that comes back is unmarked.
- **Pricing.**
  - The `prices(model_pattern, input, output, cache_read, cache_write_5m, cache_write_1h, per Mtok USD, source, updated_at)` table is seeded with the shipped list prices and is editable. Each shipped row cites the provider's public pricing page and the date it was read.
  - The shipped rows are versioned. `price_seed(id = 1, version)` records the version a database has, and `priceSeeds` in `pricing.go` keeps the table each version shipped. A version that shipped never changes; a release that changes the prices adds a version, and `TestShippedPriceVersionsAreFrozen` pins each version's digest. At every start on an older version, the seed brings each shipped row up to date. A pattern no earlier version shipped is inserted with `INSERT OR IGNORE`. A row still equal to one an earlier version shipped, in every rate and its source, is replaced with the current row, so a corrected rate or citation reaches an existing install. Then the seed records the shipped version. A row its user deleted stays deleted, and a row the user edited or added is untouched: `PUT /prices` gives every changed or new row the user's own source or "edited in dashboard", never a shipped row's source, so an edited row never matches. A database from before seed versions counts as version 1, which is the list it was seeded with. A database with a newer version than the release is left alone.
  - Seed version 3 adds the image models a Codex account serves through the images endpoints: `gpt-image-2`, `gpt-image-2.5*`, and `gpt-image-2.6*`. OpenAI lists `gpt-image-2` and the `-sunburst` and `-flare` variants of 2.5 and 2.6 at the same rates, each with separate image and text token rates. A row has one input rate and usage records do not split image from text tokens, so each row uses the image rates (input 8, output 30, cached input 2) and prices a text prompt at the image rate. `gpt-image-2` is an exact pattern rather than `gpt-image-2*`, so a later `gpt-image-2.x` gets no row instead of an older model's price. The other models upstream added with 2.6 get no row. OpenAI's page lists no `gpt-6-chat-thinking`, and `swe-2-flash`, `nemotron-3-5-super`, and `gpt-6-1-terra` are Devin models, a provider the dashboard dropped.
  - **Reset to shipped prices** in the Pricing editor (`POST /prices/reset`) replaces the whole table with the shipped rows, after a confirmation. It is the way back to shipped prices for rows the user edited.
  - Cost is computed at query time, so a price edit, a reset, or a corrected shipped rate reprices all history.
  - The dashboard labels Claude and Codex subscription costs as "API-equivalent cost".
- **Client requests.** A usage event is one upstream attempt, so a request retried on another account is two events, and a request refused before any account is tried is none. `client_requests` holds one row per request a client sent to the pool, as the client saw it, for the Dashboard's traffic, failure, and latency figures.
  - **What counts.** A `POST` to a matched route under the prefixes upstream gives a request ID (`/v1`, `/v1beta`, `/openai/v1`, `/backend-api/codex`), except token counts (`/v1/messages/count_tokens`, Gemini `:countTokens`) and realtime voice sessions (`/v1/realtime*`, `/v1/live*`). A request the guard refuses is not one. A request no account serves, or that every account refused, is one, and a failure. Model-list reads and other `GET`s are not.
  - **Websockets.** A Responses websocket (`GET /v1/responses` and `/backend-api/codex/responses` with an upgrade) is one HTTP request that lasts as long as the Codex session, often hours, so each turn is a row instead: every usage record of the connection becomes a request with one attempt, its latency, and its time to first token. A retry inside a turn is therefore counted as a turn of its own, since no taproot hook sees turn boundaries without an upstream edit. A connection refused before any turn is one failed request.
    - A turn upstream refuses before trying any account publishes no usage record, and upstream reports it only by appending to the gin context's `API_RESPONSE_ERROR` list. When the connection ends, `clientRequests` reads that list. A turn refused because no account serves the model ("unknown provider for model", with the no-accounts code the HTTP routes get), or with one of the auth manager's no-account errors (`auth_not_found`, `auth_unavailable`, `auth_disabled`, `model_cooldown`, `provider_not_found`, `executor_not_found`, `session_auth_unavailable`, or the cooldown error), becomes a failed turn with 0 attempts. Without Home mode the manager reports the attempted account's error whenever it tried one, so these errors mean no account was tried in the final round; after a retry round whose failed attempt the executor did not mark as upstream (Codex HTTP, openai-compat), such a turn can also have a failed usage record and count twice. Any other error except a client cancellation, such as a turn the per-turn API key check refused or a malformed turn, becomes such a turn only when the connection published no usage record at all, because otherwise an attempt may explain it. Ingest decides that after the 2-second settle, so a late usage record cannot make a turn count twice.
    - The errors carry no time, so these turns are dated when the connection ends, with no latency. A long Codex session can therefore show a refusal hours after it happened. Upstream's terminal-error path closes the socket after every execution error, the refusals above included, so in practice the connection ends right after a refusal and the date is close; the per-turn API key check and malformed turns leave the session open.
  - **Fields.** `ts` (start), `device_id` and `device_name` (the guard's device, as usage events have it), `model`, `provider`, `auth_index` (the last account tried), `path`, `stream`, `status` (sent to the client), `failed`, `latency_ms` (until the handler returned), `ttft_ms` (the first response byte of a stream other than an SSE comment: with `streaming.send-keepalive-before-ft` on, handlers send `: keep-alive` before the first token, and it is not one), `attempts`, `error_code`, `error_message` (at most 300 characters), and `request_id`, which is upstream's request ID: request logs and `usage_events.trace_id` carry the same one.
  - **Attempts.** Usage records carry the request ID as `TraceID`, so ingest counts the records of a running request. Codex's image tool publishes a second record for the same attempt with the attempt's start time, so a record that repeats the previous start is not counted. Upstream delivers usage records on another goroutine after the executor returns, so a finished request waits 2 seconds (`clientSettle`) before its attempts are read and it is written; the final flush at shutdown does not wait. `attempts` is 0 for a request no account was tried for. It is NULL when unknown: nothing links the request (no request ID, or more than 50,000 requests in flight), or the request was answered without an error status but none of its usage records arrived within the settle wait, so an account served it but the count is lost. Only a request answered with an error status and no usage record gets 0.
  - **Model and provider.** From the request's usage records when it has any; otherwise from the Gemini path, upstream's "unknown provider for model" error, or the first `"model"` string in the first 16 KiB of the body the handler read. While request logging is on, upstream's logging middleware swaps the body for its own copy after `clientRequests` wrapped it, so a request refused for another reason before any account (all accounts cooling, for example) can have no model. The provider of a request without usage records is guessed from the model as the no-accounts message does.
  - **Status and failure.** A stream that sent 200 and then ended in an error takes that error's status, as its request log does, and is a failure. A request the client abandoned is 499 with `error_code` `client_closed` and is not a failure: an interrupted Claude Code turn is not a fault of the pool, and counting it would make the Dashboard report trouble whenever someone presses Escape. A request is abandoned when the handler reported a client cancellation, or when the client's context was cancelled by the time the handler returned and the request's last linked attempt did not succeed (or it has none). Go cancels the context as soon as the client closes its connection, and a client may close right after the last event of a complete stream while the handler still has work left, so a cancelled context alone does not make a successful stream abandoned. Ingest decides this after the settle wait, from the last usage record; a client that cut a stream short leaves a failed record with status 499. A panic in a handler is 500 `internal_error`. `error_code` is `no_accounts`, `accounts_disabled`, or `unknown_provider` for the three no-accounts cases, `stream_error` for a stream that failed without a status, and otherwise follows the status: `bad_request`, `unauthorized`, `forbidden`, `not_found`, `too_large`, `rate_limited` (429), `client_closed`, `bad_gateway`, `unavailable`, `timeout`, `overloaded` (529), `http_4xx`, `http_5xx`. `error_message` is `error.message`, a string `error`, or `message` from the JSON (or SSE `data:`) error body, else its first line; a compressed error body gives none.
  - **Off the request path.** On the request path the middleware takes three timestamps, keeps the first 16 KiB the handler reads in a pooled buffer and the first 2 KiB of an error response, and queues the request; the database write happens on ingest's writer goroutine, in the same transaction as usage events. A full queue (50,000 requests) drops new requests and counts them with a warning. Measured with `BenchmarkClientRequests` (a streamed reply of 20 events to an 8 KiB request, 5 interleaved runs per side, medians): 12.1 to 13.9 µs per request in process (ranges 12.0 to 13.1 and 13.6 to 15.0), 5 more allocations and 2.2 KB; 219 to 225 µs over a loopback HTTP connection (ranges 218 to 221 and 223 to 230). A proxied model request takes hundreds of milliseconds to minutes. With the database locked, 200 requests still finish at once (`TestClientRequestsDoNotWaitForTheDatabase`), and the writer writes them once the lock is gone.
  - **Rollup.** `client_request_slots(slot, device_id, model)` holds requests, failures, retries, and latency and TTFT histograms per 15-minute slot (`ts / 900000`); the histograms hold only the requests the medians cover. Every zone's offset is a multiple of 15 minutes, so a local midnight starts a slot; a slot that a bucket boundary splits anyway is read from raw rows, as are the partial slots at a range's edges. `5m` buckets read raw rows only. The writer folds each flush into the slots, and ingest rebuilds them at start when their request count differs from the table's (2.4 s for 1M rows). On 1M requests over 30 days (34,572 slot rows), `GET /requests/summary` took 4 ms for 24 hours in hourly buckets, 20 ms for 7 days and 80 ms for 30 days in daily buckets (Los Angeles or Kolkata), and 6 ms for one hour in 5-minute buckets; the same 30 days from raw rows took 3.8 s. `GET /requests/recent` took 0.3 ms for the newest 5 failures and 1.2 ms for the newest 100 requests. Medians of 5 runs (`TestClientRequestsAtScale`, run with `TAPROOT_CLIENT_REQUESTS_SCALE=1`).
  - **Retention.** Like usage events, client requests are kept for good; nothing prunes them.

### Request logs

- **Storage.** Upstream's file logger wrote about 69 GB a day of raw text on the first deployment; one request can be 32 MB. Claude Code resends the whole conversation every turn, images included, and taproot logs each request twice (as received and as sent upstream). After seven weeks the first format held 645 GB of record text in 105 GB (6.1x): base64 payloads were 457 GB of it but only 3.3 GB unique, and a single image-heavy record filled a 64 MiB segment, so zstd never saw the next turn repeat it.
  - **Blobs.** Every canonical standard-base64 run of at least 1 KiB is cut out of the record text and stored once, by the SHA-256 of its decoded bytes, in pack files under `request-logs/blobs/`. The writer appends new blobs raw; the compactor re-encodes full packs with the best encoding that verifiably reproduces the bytes (Lepton for JPEG, the PNG's deflate stream replaced by preflate plaintext and corrections, zstd, or raw; see `internal/taproot/reqlog/codec`). A blob lives while a stored record references it (`last_ts`), and packs that end up mostly dead are rewritten.
  - **Codec memory.** Callers choose the images, and the native codecs' working sets dwarf their input: Lepton allocates 128 bytes per 8x8 block, so a flat 4 MB JPEG of 16384 x 16384 pixels peaked at 791 MB RSS (four in parallel at 3.1 GB) and the OOM killer then hit the same pack at every start. preflate takes about 6 bytes per plaintext byte, and level-19 zstd up to about 100 MB. `codec.Pack` reads the frame size from the JPEG's SOF or the PNG's IHDR, skips Lepton or preflate when the estimate passes 256 MiB (about 9000 x 9000 pixels at 4:2:0, or about 24 MiB of PNG plaintext), and holds the estimate in a 512 MiB weighted semaphore while native code runs; `Unpack` charges the same, reading a Lepton blob's frame size from the JPEG header Lepton stores, and a PNG blob's preflate share without the zstd match state that only encoding needs. Packs together hold at most 384 MiB of it, through a second semaphore they take first, so queued packs wait there rather than ahead of reads in the shared semaphore's FIFO, and a record view needing up to 128 MiB decodes while packs run; a pack estimated over the whole budget still holds all of it and runs alone. Behind 12 queued level-19 packs of 6 MiB blobs, a 1024 x 768 Lepton decode took 8.7 s before this and 15 ms after (median of 5 interleaved runs). Both waits end with their context, so a shutdown stops the packs still waiting instead of encoding them: work stopped 3.5 s after cancelling those packs, when the running ones finished, instead of 14.7 s. The cap costs pack throughput where level-19 zstd's 108 MiB estimate is the limit (3 at a time instead of 4): packing those 12 blobs took 20.6 s instead of 17.9 s. The large JPEG then stored as zstd at 103 MB (280 MB for four), and a 12 MP photo's Lepton output and 60 MB peak did not change (5 interleaved runs each). Once `Pack` holds its share of the budget and before it encodes, the compactor records the blob's hash in `reqlog_pack_attempts`, and deletes it once `Pack` returns, so a blob whose encoding killed the process is stored unencoded after the restart instead of killing it again. Blobs still waiting for the budget are not marked. A hard kill for any other reason during a pack also leaves the blobs it was encoding unencoded. A mark goes away when the rewrite that stored its blob unencoded commits, or when the blob is deleted.
  - **SSE transform.** In streamed replies, each delta event's text and random padding move to a payload and a varint list, leaving identical skeleton lines, and the joined text then matches the next turn's request. Kept only when it reproduces the record.
  - **Segments.** The rest of each record is a `TPRL2` frame in a per-session, per-day segment, compressed at zstd's best level with a 128 MiB window against a shared 1 MiB dictionary built weekly from recent segments' first frames. Each dictionary is an immutable file, `request-logs/dicts/<id>.dict`, kept while a segment uses it; its id is in every frame header too, so a database restored from a backup older than the segments still decodes them. A dictionary holds record text (prompts, system text, redacted headers), so retention bounds its life to about three times `max-days` from the oldest record it came from, rather than matching its records exactly: one older than `max-days` seals no new segment and is retrained (retraining runs every `max-days` when that is under a week), and the newest one goes too once it is unused and either older than `max-days` or no sealed segment is left.
  - A restored database can list as open a segment that sealed after its snapshot, so its sealed file is the only copy. The start decodes it back to a raw file. When that fails for a reason that can clear (a missing dictionary, a failed read or write), the copy is held: it stays for the next start, its dictionary is not pruned (and while a held file's header cannot be read, no dictionary is), and retention deletes it by age and size like a sealed segment, so it never stops `max-bytes`. A copy whose bytes do not decode is deleted with a warning.
  - At most 256 segments are open at once, since each holds a file descriptor and session ids come from clients; a new session past that seals the least recently written one.
  - SQLite holds `reqlog_records` (one row per record, with offsets into the uncompressed segment stream), `reqlog_segments`, `reqlog_blobs`, `reqlog_packs`, and `reqlog_pack_attempts`.
  - Viewing a record decompresses its segment up to the record, then decodes its blobs in parallel through a 256 MiB cache. The target is under 3 seconds for any record.
  - The dashboard's detail view reads `?blobs=ref&upstream=defer`: each payload is a placeholder, and the upstream request and response, which mostly repeat the client's, load when their section opens. An image shows a thumbnail from `GET /request-logs/blobs/:hash` once its JSON node is expanded; "Copy body" fetches the original. On the production copy (203,696 records, interleaved with the previous build): the largest record went from 0.91 s and 68.9 MB on the wire to 69 ms and 415 KB, a p90 record from 166 ms and 3.98 MB to 79 ms and 328 KB, and a median record kept its ~31 ms and went from 179 KB to 110 KB.
  - List filters on status (at or above 400), model, and account walk an index newest first (`reqlog_records_errors_ts`, `_model`, `_auth`); `statusClause` repeats the partial index's term so SQLite uses it. Those lists went from 56 to 166 ms to about 2 ms, stats from 95 to 20 ms. Text search without another filter still scans every record (about 280 ms). The indexes are in the schema, so an existing database builds them on its first start, about 1 s on the production copy.
  - Measured on the full production corpus before the format was accepted: all 203,341 records converted and every one rebuilt byte for byte (SHA-256 against the original text), stored in 3.55 GB against 105 GB before (29.6x): 0.95 GB of segments for 189 GB of residual text, and 2.6 GB of blobs (JPEG 2.27 GB to 1.73 GB with Lepton, PNG 0.40 GB to 0.26 GB with preflate, 0.45 GB of incompressible signatures). The detail view of the largest records (about 85 MB of JSON each) answered in 0.56 to 0.76 s.
- **Credentials.** Stored text keeps no part of a credential, where upstream's logger keeps 4 characters from each end: credential header values, the `value=` of the executors' `Auth:` line, and credential query parameters (`key`, `value`, and names with `token`, `secret`, `api-key`, and the like) in the request URL and each `Upstream URL:` become `[redacted]`. That covers each API attempt and each upstream websocket request event (`Event: api.websocket.request`). Bodies, including websocket response frames, are stored as sent.
- **Retention.** By days and total bytes, plus a path exclusion list (default excludes 404s on unknown routes, such as `HEAD /api/hello`, and the dashboard's static files).
  - `max-bytes` deletes whole sealed segments in order of their first record. Blob GC frees only blobs last used before the oldest remaining record, so that order is the one that frees blobs; deleting by newest record instead can delete every short segment ahead of a long session's segment and free nothing. One pass computes the total once, picks the segments whose bytes plus the blobs they alone pin cover the overage, deletes them 64 to a transaction, and runs GC once. On 8,000 one-record segments, halving `max-bytes` took 0.30 s against 6.4 s for the earlier one-segment-at-a-time loop. When the oldest record is in a segment that has not sealed and is not held, the pass waits for it.
  - The count is sealed segments on disk, unsealed segments at the compression ratio sealed ones reached (open segments shrink about tenfold when they seal), live blobs with their pack entry headers, and dictionaries. Dead bytes in packs are not counted, since a pack is rewritten only once a quarter of it is dead, so pack files can hold up to a third more than the live blobs; `bytesOnDisk` in `GET /request-logs/stats` includes them.
  - A 404 or 403 counts as an unrouted or guard response only when it carries no upstream request, response, websocket timeline, or upstream error. Since upstream `c3938b72b` and `be6916247`, the middleware ends a stream whose upstream failed with the error status and the upstream errors (`WriteAPIResponseErrors`, part of `logging.StreamingLogWriter` since `be6916247`), so a streamed record keeps its upstream errors as a buffered one does.
- **On and off.** Upstream's `observability.logs.request-log` in `config.yaml` is the only recording switch; taproot adds no key of its own. With it off, the middleware still forces every response with status 400 or above to be stored, with its request body, including local failures that never reached upstream, such as a malformed request; the excluder still drops unrouted 404s by default. A negative `max-days` or `max-bytes` keeps logs forever, so both limits off does not mean logging is off.
  - The Settings page's **Request logs** card shows both. Its **Record requests** switch writes `request-log` through upstream's `PUT /v8/management/config/observability/logs/request-log` and updates the dashboard's config store, after the card's `PUT /settings` succeeds, and applies the saved settings only once that write settles; when it fails the card says the limits were saved and the switch was not. Each limit is a choice between **Keep forever** and a limit, and when both keep forever the card says so with the current disk use (`bytesOnDisk` from `GET /request-logs/stats`). When recording is off the card says so and dims the limits, which still prune stored logs. Upstream's hidden request-log toggle on the System page stays.
- **Budget.** Compressed storage at or below 1 GB a day at the first deployment's traffic. The format was accepted on the production measurement above.
- **Application logs.** These stay upstream's `/v8/management/observability/logs`.

### Backups

- **Contents.** `config.yaml`, `taproot.yaml`, the auth dir's `*.json` credential files, its Codex refresh journal, and a `store.Snapshot` of the DB go into `backups/<UTC timestamp>.tar.zst` with a manifest of SHA-256 sums.
  - **Credentials.** Upstream's startup load (`FileTokenStore.List`) walks the whole auth dir and reads every `*.json` file, through a symlink too, so a backup holds the same set: files in subdirectories, and a symlinked file's content. It leaves out the refresh journal, which it stores on its own, and the data dir when it is a subdirectory of the auth dir. When the two are the same directory, its credentials are backed up. A subdirectory it cannot read is skipped with a warning. The manifest marks such a backup with `"authTree": true`. A restore makes the whole auth dir match it. It rewrites a symlinked credential's target in place with `O_WRONLY|O_TRUNC`, as upstream's `FileTokenStore.Save` rewrites an existing credential, so the target keeps its mode and its directory need not be writable. A backup without the mark, from before this, held top-level files only, so its restore leaves subdirectories alone.
  - **Size limit.** A restore reads each config, credential, and journal file into memory and refuses one over 16 MiB, so a backup refuses such a file when it is created rather than writing an archive that no restore can read.
  - **Refresh journal.** Upstream `68cd75724` records a claim in `<auth-dir>/.codex-refresh/<key>/` before it sends a Codex refresh token, and writes a `receipt` file there when the refresh finishes. A claim without a receipt is a refresh whose outcome is unknown (`refresh_outcome_unknown`), and upstream never sends that token again. Upstream's recovery guide (`docs/codex-refresh-recovery.md` in upstream `681ce41b6`, which the sync deleted) says the journal must accompany credentials across backups and restores, that restoring older credentials without it is unsafe, and that claims are never deleted to allow a retry. The archive therefore holds every directory of the journal as a tar directory member (`"dir": true` in the manifest, with no size or sum), because an empty claim directory is the unresolved state, and every regular file under it with its relative path. The journal is read after the credentials, so a claim made on a refresh token before the backup read that token is in the backup too. Because claims are never deleted, the manifest grows by about 400 bytes per claim (measured). A reader accepts a manifest of up to 64 MiB, about 160,000 claims, and a backup whose manifest would be larger fails when it is created rather than being written as an archive that no restore can read.
  - **Restore order.** The journal goes back first. A restore adds each claim directory (0700) and receipt (0600) that the auth dir lacks and syncs the directories, and only then writes the credentials. It never removes or replaces a journal entry. The live journal holds every claim made since the backup, including claims on the refresh tokens the restore puts back, and a receipt is written once by the process that made its claim. A receipt is created through a temporary file and a hard link, which fails rather than replace a file. A backup from before this has no directory members and restores as before, leaving the live journal alone. A release from before this refuses a backup that holds journal directories as corrupt, rather than restoring the credentials without them.
  - **Not backed up: `kv.db`.** Upstream's local key-value store (`server.kv-store`, default `<auth-dir>/kv.db`) is a bbolt file that the server keeps open with an exclusive lock. bbolt copies a consistent snapshot only through a read transaction in the process that holds the database, and upstream's `kvstore` package does not expose one, so taproot could get one only through a new upstream edit, and a restore would also need to swap the file while it is closed, like the DB. A copy of the file taken while it is open can be torn. Outside Home mode, which taproot refuses, it holds caches that expire, such as replay and signature caches (1 to 3 hours), session and user IDs (1 hour), Claude device profiles (7 days), and Antigravity credit hints, plus Claude session date pins, which do not expire and which the next request in a session recreates. Claude device ID pools live in the credential files, which are backed up. So taproot leaves `kv.db` out.
- **Schedule and retention.** Daily at a time in the server's zone (`TZ`, else `/etc/localtime`), default `00:00`. A file that sets `daily-at` keeps its time. Keep N (default 14).
  - The loop waits at most a minute at a time and runs when the wall clock reaches the time. Its timer runs on the monotonic clock, which stops while the host is suspended and ignores wall clock steps, so one long wait could run a backup late by the suspend or early by a step. It remembers the time it last ran for and never runs for that time again, so a clock stepped back after a run does not repeat it.
  - Listing reads each archive's manifest once and caches its file count by name, size, and modification time. Reading a manifest allocates the zstd decoder's window, about 8 MB for a sizeable archive, and every page load and backup lists.
  - On a DST change, a repeated time runs at its first occurrence. A skipped time runs as far past the gap as it fell inside it, so `02:30` on a day that jumps from 02:00 to 03:00 runs at 03:30.
  - **Last run.** Each scheduled run writes its outcome, the time and the error or none, to `backup_scheduled_run`, one row that the next run replaces, so the Dashboard can say the last run failed after a restart. A run skipped because a restore waits for a restart, or cut short by shutdown, writes nothing.
  - The server's zone can differ from the browser's, so Settings and Backups show the next run twice: in server time with the server zone's name, and in the browser's time with its zone's name. Backup creation times carry a zone label.
- **Endpoints.** List, create now, download, and restore.
  - **Checks before anything changes.** Restore verifies the archive (422 `corrupt_backup`) and refuses a database that lacks a declared column (409 `incompatible_backup`). It keeps the current values of the keys that say where this server keeps things, `data-dir` and `store.path` in `taproot.yaml` and the auth dir in `config.yaml`, because the database is staged in the current data dir and the credentials go to the current auth dir; a backup's older values would point the next start at an empty database. Upstream v8 names the auth dir `oauth.auth-dir` and still reads the older top-level `auth-dir`, so each form takes the current file's value or is removed when the current file lacks it, and the restored file names the auth dir only the way the current file does. It then reads the resulting `taproot.yaml` as `setup` will, with the strict decode and the access list checks, and refuses a file the next start would refuse (409 `incompatible_backup`), such as one with a renamed key or an address that covers Tailscale's ranges. Without this, the restore succeeded and every start after it failed, which needs a shell to fix. It also refuses a file whose data dir or database is not the running server's, which happens after an edit that was not restarted yet. Last, a tailnet caller is refused with 409 `would_lock_out` when the restored file would not give its device Admin or turns the guard off, unless the body is `{"allowLockout": true}`. The Backups page shows that refusal in the restore dialog, whose button then reads "Restore anyway" and resends with `allowLockout`; it names `incompatible_backup` and `restart_pending` refusals too. After a restore that restarts, the page probes the server every 2 s for 90 s. Three 403 answers in a row (other than `server_node_unknown`) read as "back, but it refuses this device" rather than "has not come back", worded by the code: `guard_disabled` says the restored file turns the guard off, `unknown_host` says the server no longer answers to the page's host name and points at `access.extra-hosts`, and any other code shows the server's message. A starting server answers `unknown_host` to its own MagicDNS name until it has read tailscaled, so that code needs ten in a row (20 s). Probing goes on for the full 90 s, so a refusal that clears ends as "back". A `not_admin` answer never reaches the banner, because the connection gate replaces the page with its request screen. Loopback callers are admins whatever the lists say. Only `taproot.yaml` is checked: `config.yaml` is upstream's, loaded leniently, and its loader writes to the file it reads.
  - Restore writes the current state to a pre-restore backup first.
  - It then adds the backup's refresh journal entries (see Contents), replaces the config files and credential files, and restarts the database from the snapshot on the next start. The restore marker names the database relative to the data dir, so a data dir mounted at another path still finds it. A marker whose database is neither staged nor swapped in logs a warning.
  - On unix, taproot then sends itself SIGTERM, drains as on any shutdown (see "Shutdown drain"), and exits with status 75 (EX_TEMPFAIL), so its supervisor starts it again and the next start swaps in the database. A clean exit, status 0, would leave it stopped under a restart policy that restarts only failures, such as systemd's `Restart=on-failure` or Docker's `on-failure`. The shipped units use `Restart=always` and `unless-stopped`, which restart either way. Where a process cannot signal itself, the restore answers `restart: manual` and the operator restarts taproot.
  - **Until the restart.** The restored files wait for their database. Until the process restarts, another restore, a new backup, a settings save, and the tailnet sweep get 409 `restart_pending` or skip, since each would mix the restored files with the running database or write the running access lists over the restored ones. Restore and the settings writes share one lock on `taproot.yaml`, so neither replaces the other's file halfway through a read-modify-write.
  - **Durability.** Every rename that publishes a file (an archive, a restored file, the marker, the swapped database, and `taproot.yaml` from settings) is followed by an fsync of its directory. Some filesystems cannot fsync a directory and return EINVAL, EBADF, or ENOTSUP, which PostgreSQL's `fsync_fname` also ignores for directories; taproot ignores those too. Any other error from that fsync is logged and the write still succeeds, because the rename has already put the file in place. The refresh journal's directory syncs, which must finish before any credential is written, still fail the restore on such an error. A journal receipt is linked into place so it never replaces a file; on a filesystem without hard links (some SMB, 9p, and FUSE mounts) it is renamed into place after a fresh check that none exists, as upstream writes receipts.
- **Security.** Backups contain OAuth tokens. They stay under the data dir with mode 0600.

### Alerts

Taproot posts to one Discord channel through a webhook. The webhook URL is the only setting.

- **Config.** `alerts.discord-webhook` in `taproot.yaml`, plus `alerts.enabled` (default on when a webhook is set). Settings shows whether a webhook is set by its last six characters only, and sets, replaces, or clears it. The server accepts only `https://discord.com/api/webhooks/<id>/<token>` and its `discordapp.com`, `ptb.`, `canary.`, and `/api/v<n>/` forms. The URL is a credential: it is never logged, never returned by the API, and lives only in `taproot.yaml` (and so in backups, which are 0600). An invalid webhook in a hand-edited `taproot.yaml` does not stop the server: alerts log an error without the URL, stay off, and settings report `webhookInvalid` until the webhook is replaced or cleared.
- **Scope.** Alerts watch the accounts the manager lists and the user has not disabled. Upstream sets `Disabled` and `StatusDisabled` only from the auth file's `disabled` switch, so a disabled account is out of scope whatever its last error. When an account is removed or disabled, its open alerts, and its provider's pool alert once the provider has no accounts left, are dropped without a recovery.
- **Events.** Each has a stable dedupe key.

  | Event | Key | Fires when | Recovery |
  |---|---|---|---|
  | Limit hit | `limit:<authIndex>:<window>` | A window's latest observation is `rejected` or at utilization 1 or more, and its reset is still ahead. With no reset known, the limit ends one window length after the reading, or holds until the next reading when the length is unknown too. A Codex window is named by its length (5-hour, weekly, monthly), since either header slot can hold any of them | The window is below its limit, or its reset passed |
  | Pool empty | `pool:<provider>` | Every account of the provider is at an account-wide limit or has a broken login that no longer serves. When a broken login is part of the reason, the condition must hold for 2 minutes, like the login alert. The message names the first account back and when | One account is usable |
  | Login broken | `login:<authIndex>` | For 2 minutes, upstream marks the credential `RequiresSignIn` or a terminal 401 (`HasUnauthorizedAuthFailure`). The message carries upstream's sanitized reason. Upstream keeps serving a `RequiresSignIn` account while its access token is valid (`canServeWithAccessToken`), so then the message says it keeps working until the token expires, and the account still counts as usable for the pool | The credential works again |
  | Reset grant expiring | `grant:<authIndex>:<grantId>` | A Claude `cedar_ember` grant has resets left and ends within 24 hours. It warns once per grant: the episode stays open until the grant ends, even while a read is missing | None |

  The login alert warns as soon as the refresh credential is rejected, rather than waiting for the access token to expire, so there is time to sign in again before the account stops serving.
- **Flapping.** A key alerts once per episode. A recovery waits until the condition stays clear for 2 minutes, so a shorter flap continues the episode. A new alert for the same key waits 30 minutes after the previous one.
- **Delivery.** An alert counts as posted only once Discord accepts it: the sender reports each message's outcome back to the evaluation, which owns the detector. Until then a recovery for the key waits, so the channel never gets a recovery for an alert it did not see. A failed delivery forgets the alert, so it is sent again while the condition holds, and gets no recovery when the condition clears first. A failed recovery is sent again, and the key does not alert again until its recovery is delivered. Each failure in a row waits longer before the next try: 1 minute, then 2, 4, 8, and 16, then every 30 minutes. A message dropped because the queue was full counts as a failure too, so a full queue cannot make the evaluation queue it again at once. A message the queue skipped because alerts were off is not a failure and goes out at the next evaluation once alerts are on. An alert or recovery still in the queue at shutdown is sent after the restart. A new webhook gets every alert that is still open, after "Webhook connected", and no recovery of an alert it never received. The detector's state is stored in `alert_state`, so a restart neither repeats an alert nor drops a pending recovery. Upstream keeps `RequiresSignIn` and `RefreshError` in memory only, so after a restart a broken login looks healthy until a refresh fails again. A login alert that was open at the restart therefore stays open, for the login and the pool, until a refresh succeeds after startup or the account's access token changes.
- **Sources.** Quota comes from ingest in-process: `Ingest.OnQuota` publishes every observation of a committed flush to each subscriber (alerts and routing), and `LatestQuota` seeds the module at start. Account state comes from the auth manager, which `taproot.go` attaches in the router configurator. Quota rows of accounts the manager no longer lists are ignored. Nothing is evaluated while alerts are off or before the manager has loaded.
- **Reset grants.** For each Claude account in scope that does not need sign-in, at most every 3 hours, alerts reads `GET https://api.anthropic.com/api/oauth/usage?cedar_ember=1&skip_spend=1` with the account's current access token, as the dashboard's `claudeResetGrants.ts` does. It takes the same route as the quota poller (see "Polling idle accounts"). Grants from a read more than 6 hours old, because the reads since then failed, are not alerted on, so a grant redeemed in the meantime stops warning. It never refreshes a token and never redeems a grant.
- **Card layout.** Each message is a Components V2 card (flag `1 << 15`), the layout chosen from mockups posted to a test channel: one container with the severity's accent color, a section with the `###` title and the description beside the logo thumbnail, a divider, the fields as `**Label** value` lines, and a `-# Taproot · <t:…:f>` footer. The sender name is `Taproot` and the avatar is the logo. A channel webhook accepts components only with `?with_components=true`, so every post goes to `?wait=true&with_components=true`, on the test origin too. The card stays within Discord's limits: about 8 of the 40 components, and the title (256 characters), description (2,000), and fields (25 lines of at most 1,024 characters each) are cut so the text stays under 4,000 characters. Times use Discord's `<t:…>` markup, so each reader sees local time. `allowed_mentions` is empty and labels are markdown-escaped, so account or grant text cannot ping or reformat.
- **Logo.** Discord fetches the avatar and thumbnail itself from `https://raw.githubusercontent.com/265866/taproot/main/internal/taproot/alerts/assets/taproot.png`, so a tailnet-only server needs no upload and the webhook needs no change. The PNG is the favicon mark at 256x256, rendered by `scripts/taproot/render-logo.ts` with resvg-js installed into a temporary directory. `logo_test.go` pins the path, since a move breaks the image in every message, and compares the favicon in `web/index.html` with the SVG hash in `assets/taproot.svg.sha256`, so a changed mark fails until the PNG is rendered again. The image depends on the repository staying public.
- **Connected message.** When `PUT /settings` saves a new non-empty webhook and `taproot.yaml` is written, settings queue one "Webhook connected" message (Info) if alerts are active. It goes through the same queue as alerts, so the request never waits for Discord. Saving a new webhook does not wake the evaluation itself; the announcement queues its message first and then wakes it, so alerts that are already due arrive after "Webhook connected".
- **Access requests.** When the access module opens or reopens a request (see "Access requests" under "Access"), it queues one "Access requested" message (Info), keyed `access:<stable ID>`, that names the device (its own name, else its Tailscale name, else "A device"), its login, its client, and its ID, and points at Requests on the Access page. A refusal of an open or allowed request queues nothing. It follows the alerts switch and webhook like every message, and the text goes through the same markdown escaping as account labels.
- **tailscaled.** The access guard's monitor (see "tailscaled while running" under "Access") calls `Tailscaled` once when tailscaled's LocalAPI has failed for 2 minutes and once when it answers again. Both messages share the key `tailscaled`, so a recovery replaces an outage message still in the queue. The outage card (Critical) names the socket, how long it has failed, the error, and the fix: restart taproot for a missing or refusing socket, else check tailscaled. The recovery card (Recovered) says how long it lasted. Neither goes through the detector, because the monitor already debounces and sends each once; a restart of taproot during an outage starts the count again. It follows the alerts switch and webhook like every message.
- **Queue.** One sender drains a queue that holds at most one message per key: a newer message for a pending key replaces it in place. The detector queues a recovery only after its alert was delivered (see "Delivery"); the tailscaled recovery, which says how long the outage lasted, may still replace its outage message. The queue holds up to 256 keys and drops a message for a new key beyond that, with a warning, so the proxy never waits; the detector retries a dropped alert or recovery after the failure delay. The sender honors `retry_after` on 429 and retries network errors and 5xx with backoff. It gives up after 4 attempts or once the next wait would take the message past 1 minute of waiting, and logs failures without the URL.
- **Test button.** `POST /taproot/api/v1/alerts/test` makes one delivery attempt within 10 seconds. A 429 from Discord returns 429 `rate_limited` with Discord's `retryAfter`; other failures return Discord's status.
- **Delivery health.** `DeliveryHealth` counts the failed deliveries since the last success, with the first failure's time and the last error, which names Discord's status or the network error and never the webhook. It counts every message the queue sent or dropped as full, recoveries and announcements included, but not the messages the queue skipped. A successful test send counts as a delivery, so the Dashboard's item clears once the user's test reaches Discord; a failed test is not counted. A new webhook starts the count again, and an undone Settings save puts the old count back with the old webhook. Turning alerts off and on keeps the count, because nothing has tested the webhook since. It lives in memory, so a restart clears it until the next failure. The Dashboard lists it while alerts are on (see "Status").
- **End-to-end testing.** `TAPROOT_ALERTS_DISCORD_ORIGIN=http://127.0.0.1:<port>` sends deliveries to a local fake Discord. It keeps the webhook path and replaces only the scheme and host. Only loopback origins (`127.0.0.1`, `localhost`, `::1`) are accepted, with the same check as ingest's `TAPROOT_DEV_*` overrides, because the webhook token travels in the path. An active override logs a warning; another origin is ignored with a warning.

### Status

The Dashboard's right rail and verdict answer "is everything OK, and what needs me?" from the server, so the page, its sidebar badges, and later the Discord alerts read one judgment. `internal/taproot/status` owns no tables. Each read of `/status`, `/attention`, or `/pools` gathers the auth manager's credentials, ingest's latest quota and the last 9 hours of quota observations, the client requests of the last 15 minutes and the last hour, the open access requests, the backup list and last scheduled run, the alerts' delivery health, and the tailscaled monitor's last report, then judges them at one instant. Evaluations run one at a time. A background evaluation every 30 s keeps the start times below accurate while no dashboard is open. When the quota or the client requests cannot be read, the three endpoints answer 500; when the access requests or the backups cannot be read, they still answer, and Needs you lists what it cannot see.

- **Account states.** Each credential is `serving`, `cooling`, `signed_out`, or `disabled`. `disabled` is the user's switch (`Disabled` or `StatusDisabled`). `signed_out` uses the alerts module's login rule: upstream marks the credential `RequiresSignIn` or a terminal 401, and its access token no longer serves. A sign-in-required account whose current token still serves stays `serving` with `refresh failing`. `cooling` is a credential-wide cooldown in upstream's `CooldownSnapshotForAuth` (a cooldown on some models leaves the account serving the others), or an account-wide quota window at its limit by the alerts module's limit rule; it ends at the later of the two, unknown when one is unknown. Upstream never disables a credential after an error, so "disabled by an error" has no signal of its own (see Needs you).
- **Pools.** `projection.go` ports the Accounts page's quota model (`web/src/features/taproot-quota/model/projection.ts`) line for line, and `projection_test.go` checks it against the same cases and numbers as `taprootQuotaProjection.test.ts`. The Accounts page keeps its own copy for now. A pool counts usable accounts only: `leftNow` is the quota left on serving accounts, in accounts (1 is one account's whole window), and `percentLeft` is that share of the enabled accounts, so a signed-out or cooling account lowers it. Quota on signed-out and disabled accounts is `lockedAccounts`; on cooling accounts it is `waitingAccounts`, with the earliest time one is back. An account without an observed window counts as full, as on the Accounts page.
  - **Next reset** is the Accounts page's definition: the first reset that gives capacity back if usage stopped now, over serving and cooling accounts, because a cooling account's reset brings it back on its own.
  - **Burn** is the drop of the serving accounts' recorded pool over the last 3 hours, as a share of the enabled accounts per hour. It ignores the Dashboard's window.
  - **Run-out** projects the serving accounts at each window's 3-hour burn rate, without moving load from an account that empties to another, as the Accounts page does, up to 8 days ahead. `runsOutAt` is when they are all empty, now when none serves, and null when they last the 8 days. `lastsPastReset` is true when the next reset comes first.
- **Verdict.** `normal`, `degraded`, or `down`, with the reasons behind it:
  - `down` when no account serves a provider that had a client request in the last hour, or when at least 50% of at least 20 client requests in the last 15 minutes failed.
  - `degraded` when at least 5% of at least 20 client requests failed, or a provider that had traffic in the last hour is down to one usable account. A provider with only one enabled account is not down to one: that is its normal.
  - A request the client abandoned (499 `client_closed`) is not a failure (see "Client requests"). Fewer than 20 requests are too few to judge: two failures of three are not an outage.
  - The headline is "Serving normally", "Degraded: 6% of requests failing in the last 15 min", "Degraded: Codex is down to one usable account", "Down: no account can serve Claude", or "Down: 62% of requests failing in the last 15 min"; the percentage is rounded down, so it never shows a threshold the requests did not reach. A provider reason comes before the failure rate, because it names what to fix. The detail line reads like "No failures in the last 15 min · 4 of 5 accounts can serve (Claude 3, Codex 1)". `since` is when this server first saw the state; a restart starts it again.
- **Needs you.** Items sort by severity (`blocking`, `at_risk`, `waiting`, `overdue`), then oldest first. Each has one action. An item whose data has no start time (a low pool) keeps the time it was first listed, until it clears.

  | Kind | Severity | When | Action |
  |---|---|---|---|
  | `account_signed_out` | blocking | A credential is `signed_out`. The detail gives the reason (see "Login reasons"), how many accounts still serve, and the quota locked on it | `sign_in` (provider) |
  | `account_refresh_failing` | at_risk | Upstream can no longer refresh the login, but the current access token serves until it expires | `sign_in` (provider) |
  | `account_disabled` | blocking | The account is disabled, no account of its provider serves, and the provider had client requests in the last hour. A disabled account is otherwise the user's choice and needs nothing | `enable` (auth index) |
  | `pool_low` | at_risk, or blocking when no account serves but some are cooling | The pool runs out before its next reset, or has under 15% left. Cooling accounts are named here instead of listed on their own, because they matter only when the rest of the pool cannot carry the load until they are back. A pool with no serving or cooling account gets no item: its signed-out or disabled accounts have their own | `open_accounts` (provider) |
  | `access_request` | waiting | An open access request of a device without both permissions, as the Access page lists them | `review_access` (node ID) |
  | `backup_overdue` | overdue | While the daily schedule is on: the newest backup of any kind is over 26 hours old (a day plus room for a slow run; with none, 26 hours after this process started), or the last scheduled run failed and no backup was written after it | `backup_now` |
  | `alerts_failing` | at_risk | Alerts are on and the last deliveries to Discord failed (see "Delivery health" under "Alerts") | `open_settings` (`alerts`) |
  | `source_unreadable` | at_risk | The access requests or the backups could not be read, so their items cannot be listed. The detail gives the error, and the server logs it once until the source reads again. An unreadable backups source replaces `backup_overdue`, and is listed only while the daily schedule is on | `open_logs`: the Logs page's app-log tab, which has the warning only with `logging-to-file` on; without it, the page says to read the server's own log (stdout or the journal) |
  | `tailscaled_down` | blocking | The access guard's tailscaled monitor reported an outage and no recovery since | `docs` (the troubleshooting entry) |

  `counts` gives the items per sidebar area: `accounts` (the account and pool items), `access` (access requests, tailscaled, and unreadable access requests), and `backups` (including unreadable backups).
- **Login reasons.** A signed-out or refresh-failing account's detail starts with why. A failure upstream names by a known code (`refresh_outcome_unknown`, `refresh_token_reused`, `refresh_token_expired`, `refresh_token_invalidated`, `token_revoked`, `invalid_grant`, `invalid_client`) reads as a plain-English sentence without the code; so does upstream's renewal state when there is no failure text (`sign_in_required`, `expired_sign_in_required`, `retry_scheduled`). Any other text is upstream's sanitized message (`SanitizeRenewalMessage`), which redacts tokens, codes, and URLs.
- **Text.** Titles and details are English sentences the page shows as they are. They name times relative to now ("in about 2 h 40 min"), never as clock times, because the server's zone is not the reader's; the structured fields carry RFC 3339 times for a page that formats its own.
- **Cost.** One evaluation runs four small indexed reads: the latest quota (one seek per account window), 9 hours of quota observations, and two counts over the client requests of the last hour, which `client_requests_ts` serves. See "Status cost" under "Decisions" for the measurement.

### Web

- `web/` builds to `dist/index.html` and content-hashed chunks under `dist/assets/`, one per route page.
- `internal/taproot/web` embeds `internal/taproot/web/dist/` and serves `index.html` at `/` with `Cache-Control: no-cache` and an ETag, and the chunks at `/assets/*` with `Cache-Control: public, max-age=31536000, immutable`. Each file is gzipped once at startup and sent gzipped when `Accept-Encoding` allows; browsers offer only gzip and deflate to a plain-http tailnet name.
  - The build copies `web/dist/` there.
  - A committed placeholder `index.html` keeps `go build` working without a web build.
  - A tab still running an older build reloads once when a page chunk it asks for is gone.
  - The chunks, like the page, hold no data, and the guard admits the same callers to both (see "Security model").
  - Request logs record neither: upstream's logging middleware skips GETs, and the request-log excluder drops `HEAD` of `/` and `/assets/*`.
- Why it was one file, and why it no longer is.
  - The Management Center shipped as one downloadable `management.html` that upstream fetches into its data directory and serves, so it had to be self-contained. Taproot's guard 404s that file and embeds its own build, so the constraint no longer applies.
  - One file meant every visit downloaded and compiled the whole app (2.8 MB, sent uncompressed with `no-store`) before the connection gate could render, over a 20 Mbps tailnet link. Now the page is a small revalidated `index.html` (`no-cache` and an ETag, so an upgrade shows on the next load and an unchanged page costs a 304), and the code sits in hashed chunks that are immutable for a year, so a repeat visit downloads nothing but the page's 304, and a first visit downloads only the shell and the current page's chunk, gzipped.
- The dashboard calls the management API at same-origin `/v8/management` with no key, and taproot at `/taproot/api/v1`.
- The login screen and the management-key flow are removed.
- Upstream's `/management.html` returns 404 from the guard. Deployment also sets `remote-management.disable-control-panel: true` so the panel is not downloaded.

### Nix

- `flake.nix` and `nix/` package taproot for `x86_64-linux` and `aarch64-linux`, Linux only like the image. They live here, not in a separate repository, because the build reads `go.sum` and `web/bun.lock` from the tree. Upstream has neither path, so syncs never conflict there.
- The flake has three packages, one per stage of `Containerfile.taproot`:
  - `taproot-codec` (`nix/codec.nix`) builds `internal/taproot/reqlog/codec/native` with `rustPlatform.buildRustPackage` and its `Cargo.lock`. nixpkgs' cargo hook sets `ZSTD_SYS_USE_PKG_CONFIG`, which would link a system libzstd that the server's cgo flags never name, so the derivation unsets it and zstd is compiled into the static library, as in the image.
  - `taproot-web` (`nix/web.nix`) builds the dashboard with nix-community's bun2nix, because `bun.lock` has 40 platform-specific entries that one fixed-output hash of `node_modules` cannot cover. bun2nix generates `web/bun.nix` from `web/bun.lock`, one fetch per package. The build sets `VERSION`, because `vite.config.ts` otherwise runs `git describe`, and installs with `--linker=hoisted`, the layout `bun install` gives `web/` everywhere else: under bun2nix's default isolated linker, `tsc` fails, because the sources import packages that `package.json` does not list, such as `react-router`.
  - `taproot` (`nix/taproot.nix`) is `buildGoModule` with Go 1.26, `go.mod`'s line. nixpkgs builds with `GOTOOLCHAIN=local`, so a Go older than `go.mod`'s `go` line fails in the module download, which a user whose taproot input follows an older nixpkgs hits (measured: nixpkgs `baa82799` has Go 1.26.9 and fails with `go.mod requires go >= 1.26.10`); an assertion stops evaluation first with both versions and the fix. It builds `cmd/server` with the `taproot_codecs` tag and cgo, renamed `taproot`. `postInstall` puts `LICENSE`, `THIRD_PARTY_NOTICES.md`, `web/LICENSE`, and `licenses/` in `share/doc/taproot/`, at the relative paths the notices link to, because the codec statically links an LGPL-3.0 crate (see "LGPL crates"); `meta.license` lists MIT and LGPL-3.0-or-later. `preBuild` copies the dashboard into `internal/taproot/web/dist/` and the codec library into `native/target/release/`. `overrideModAttrs` clears `preBuild` for the module download, so `vendorHash` (`nix/vendor-hash`) depends on `go.sum` alone.
  - A flake has no tags to describe, so `main.Version` is `package.json`'s version, which the release PR bumps with the manifest (`extra-files` in `.github/release-please-config.json`), with the commit date (`0.1.0-unstable-2026-11-08`), `main.Commit` the flake's short revision, and `main.BuildDate` the commit time.
- `web/bun.lock` had 72 packages with an empty integrity field, which bun2nix turns into an empty hash that no build accepts. They were filled in from the npm registry at the same versions, and `bun install --frozen-lockfile` into an empty cache downloaded and accepted all of them.
- **Hashes.** `scripts/taproot/nix-refresh.sh` regenerates `web/bun.nix` with the bun2nix in `flake.lock`, refuses a lockfile entry without integrity, and recomputes `nix/vendor-hash` by building the module download with a placeholder hash. A plain build would not do: a stale hash whose output is already in the store builds without fetching. CI's `nix-hashes` job runs the script and fails on a diff. It does not push the fix, because a commit pushed with the workflow token starts no CI run, so that head would go unchecked. On Renovate's branches, `renovate-refresh.yml` pushes the fix and starts CI itself (see "Dependency updates"). `sync-upstream.sh` runs the script as its `nix hashes` check when Nix is installed, and reports the check skipped otherwise.
- **NixOS module** (`services.taproot`, `nix/module.nix`):
  - Nix owns `config.yaml`. It is written from `settings` on every start, mode 0600 and not a symlink, so a dashboard edit to it lasts until the next restart. `taproot.yaml` is copied from `taprootSettings` only while the file does not exist, because the dashboard owns it afterwards and saves it by renaming a new file over it. Changes to `taprootSettings` therefore apply only on the first start, and the option's description says so. Taproot does not start without `taproot.yaml`, so an assertion refuses an empty `taprootSettings` rather than letting the unit restart forever; the option's description and the assertion's message say it must grant a device `admin: true`, because `IPAddressDeny=localhost` leaves no other way into the dashboard. Like the listen-address assertion, it reads no access keys.
  - `settings` and `taprootSettings` pass through the world-readable Nix store, and the options say so. The Discord webhook is a secret, so `discordWebhookFile` names a file outside the store instead. The unit reads it with `LoadCredential`, and `preStart` writes it into `taproot.yaml` with `yq` while it seeds that file, before moving the file into place, so it follows `taprootSettings`' first-start rule and a failed edit leaves no half-seeded file. A warning names `taprootSettings.alerts.discord-webhook` when it is set.
  - Outside a container every local process can connect from loopback, and the guard treats loopback as an admin (see "Security model"). The unit sets `IPAddressDeny=localhost`, which drops loopback traffic in both directions, and an assertion accepts only a literal Tailscale address as `settings.server.host`: an IPv4 address in `100.64.0.0/10` in plain decimal, or an IPv6 address in `fd7a:115c:a1e0::/48` in brackets, so taproot listens on `tailscale.address`. A blocklist of loopback and wildcard spellings is not enough, because `netdns=cgo` hands the host to glibc, which reads `0` as the wildcard address and `0x7f.1` as loopback (measured with `net.Listen`). Upstream listens on `host:port`, so a bare IPv6 address cannot listen; the default brackets an IPv6 `tailscale.address`. A local process then reaches taproot only through the Tailscale address, as the server's own node, which is proxy-only. The assertion names no access keys, so the `taproot.yaml` access format can change without it.
  - `IPAddressDeny` also drops outbound loopback, such as a `proxy-url` or DNS stub on 127.0.0.1. `GODEBUG=netdns=cgo` sends name lookups through glibc, which reaches nscd or systemd-resolved over unix sockets; Go's own resolver would send them to the loopback stub in `/etc/resolv.conf`.
  - The unit starts after `tailscaled.service` and allows `AF_UNIX` for its socket (`/run/tailscale/tailscaled.sock`, which taproot's default `/var/run/...` path resolves to) and `AF_NETLINK` for Go's interface listing. `Restart=always` also covers a start before tailscaled has assigned the address. `TimeoutStopSec=45` and `UMask=0077` match the quadlet example. The stop timeout only bounds a stop that hangs: upstream's `Stop` closes the server without draining, so a stop or restart cuts streams in flight. `openFirewall` opens the port on the Tailscale interface only.
- **VM test** (`nix/test.nix`, `checks.<system>.nixos`). Two VMs share a link with tailnet addresses, and a fake tailscaled written in the test answers `whois` and `status` on the socket. It is a `Type=notify` unit that reports ready once the socket listens, because taproot exits at startup when the socket refuses connections. The test checks that an admin device gets the real dashboard build, `/taproot/api/v1/me`, and every device on `/access/devices`; that a device with Proxy but not Admin reaches `/v1/models` and gets `not_admin` on the API; that a device with no grant gets `no_proxy` and `not_admin`; that the server's own processes are refused the admin surface; that `discordWebhookFile` seeds the webhook into `taproot.yaml`; and that a restart rewrites `config.yaml` and keeps `taproot.yaml`. Its `taproot.yaml` is the `taprootSettings` attribute at the top of the file.

### Dependency updates

- The Mend Renovate GitHub App opens update pull requests from `renovate.json`, on a weekly schedule. It reads only the files in `includePaths`: `go.mod`, the codec's `Cargo.toml`, `web/package.json` and `web/bun.lock`, the workflows, `Containerfile.taproot`, and `flake.nix`. That keeps upstream's examples, plugin test fixtures, and the codec's `patches/` out of it.
- **Go.** Only the modules whose versions taproot owns get updates: `modernc.org/sqlite`, `github.com/klauspost/compress`, and `github.com/andybalholm/brotli` (see "Upstream boundary"). Every other `go.mod` line is upstream's, and a change to it conflicts with the next sync, so upstream's updates arrive through the sync instead. The SQLite driver's indirect dependencies (`modernc.org/libc`, `mathutil`, `memory`, `github.com/ncruces/go-strftime`, and `github.com/remyoudompheng/bigfft`) are taproot's too, but they get no updates of their own: `modernc.org/sqlite` needs the exact `modernc.org/libc` version its own `go.mod` names, and `go get` of a new driver version raises them to what it requires. Updates run `go mod tidy`. The `go` line stays upstream's, so `GO_VERSION` and the golang image get digest updates only. "Upstream boundary" names each of these `go.mod` lines with its version, and a driver update can raise more of upstream's requirements, so a Go update pull request must update those entries, and add any newly raised line, before it merges. CI cannot catch a stale entry, because `check-upstream-boundary.sh` checks only that `go.mod` is named, so the rule's `prBodyNotes` puts the reminder in each such pull request's description.
- **Images and toolchains.** The dockerfile manager substitutes each `ARG` default into its `FROM` line, so it updates all four base-image digests and the Bun version. It cannot update `RUST_VERSION`, because the tag adds `-slim-bookworm` to the version, so a regex manager matches `RUST_VERSION` together with the rust digest, looks the tag up with the suffix, and rewrites both. A second regex manager moves the codec job's `RUST_VERSION` in `ci.yml` in the same pull request. The Bun image and `packageManager` in `web/package.json` share a pull request too.
- **Merging.** Digest pins and digest updates of the base images merge themselves once CI passes (`automerge` with `automergeType: pr`; `platformAutomerge` is off because the repository does not allow GitHub's auto-merge). An image digest update keeps the tag, so it brings only the rebuild that the tag already points to. An action's digest update is different: actions are pinned as `<sha> # vX.Y.Z`, so a new digest means the version tag was moved to another commit, which is how a compromised action spreads. `release.yml` runs most actions with `id-token`, `packages`, and `attestations` write permissions, and CI never runs it, so a passing CI says nothing about them. Action digests therefore wait for a person, with a `prBodyNotes` reminder to check why the tag moved. Everything else waits for a person too. Related updates share a pull request: the image digests, the action digests, the Rust toolchain, Bun, the SQLite driver, the compression libraries, the codec crates, the dashboard's non-major updates, the GitHub Actions, and the flake inputs, which change only through `flake.lock` maintenance.
- **Generated files.** The hosted app cannot run post-upgrade commands, so a Renovate pull request that changes `go.sum`, `web/bun.lock`, the codec's `Cargo.lock`, `flake.lock`, or `RUST_VERSION` in `Containerfile.taproot` (which `THIRD_PARTY_NOTICES.md` records) leaves `nix/vendor-hash`, `web/bun.nix`, and `THIRD_PARTY_NOTICES.md` stale, and CI's `nix-hashes` and `notices` jobs fail. `.github/workflows/renovate-refresh.yml` fixes that on `renovate/` branches of this repository whose pull request Renovate opened. Its `generate` job runs `scripts/taproot/nix-refresh.sh` and `third-party-notices.ts` with read-only permissions and uploads the three files. Its `push` job, which runs none of the pull request's code, commits them as `github-actions[bot]`, pushes with the workflow token, and starts `ci.yml` for the branch with `workflow_dispatch`, because a push with the workflow token starts no workflow and `workflow_dispatch` is exempt. The checks then attach to the new head. It retries the dispatch, because a rerun cannot recover one that failed after the push: the rerun commits on the old head, and its push is rejected. If every try fails, the job prints the `gh workflow run ci.yml --ref <branch>` command that starts CI by hand. It cannot loop: the push starts no workflow, so not the refresher either, and the CI run pushes nothing. The push fails rather than overwriting when Renovate pushed again meanwhile, and that newer push starts its own run. `renovate.json` lists `github-actions[bot]` in `gitIgnoredAuthors`, so Renovate still treats the branch as its own and keeps rebasing it.

### Automatic updates

- Updates are manual by default: pull the new release and restart. Automatic updates are an opt-in host script, `scripts/taproot/taproot-update`, with the user units `examples/taproot/taproot-update.service` and `taproot-update.timer` and the settings file `examples/taproot/taproot-update.env`. Nothing in taproot's code checks for or applies updates.
- **Why not `podman auto-update`.** The plan was `AutoUpdate=registry` with a `sigstoreSigned` policy in `policy.json`. That policy accepts a keyless Fulcio certificate only by `subjectEmail`, and a GitHub Actions certificate names a workflow URI with no email (`containers-policy.json(5)`; containers/image#2235, which would accept a URI, closed unmerged). Podman could therefore check only that an image is signed by someone, not that taproot's release workflow signed it. A cosign key pair would fix that but adds a long-lived secret to guard and rotate. The script checks the keyless identity with cosign instead.
- **What it follows.** The script moves a local tag, `localhost/taproot:current`, so the quadlet it updates must run that tag with `Pull=never`. `examples/taproot/taproot.container` runs `ghcr.io/265866/taproot:0.5` with manual updates, the default; the opt-in steps in `docs/updating.md` point the quadlet's `Image=` at `current` and run the script once. With no local tag, that run verifies, pulls, and tags the release. `docs/updating.md` tells the operator not to tag the image by hand: step 3 below skips a release the local tag already has, so a hand-tagged image would never be verified. A quadlet left on the `ghcr.io` tag keeps running the old image after the script restarts it, so the image-ID check in step 7 fails and the run rolls back. It follows one tag of `ghcr.io/265866/taproot`, such as `0.2`: patch releases install themselves, and a new minor version, which may change `taproot.yaml` (see `docs/stability.md`), never does. A rollback stays within the minor version, which `docs/stability.md` says is safe on the same data.
- **One run.**
  1. Take a per-unit `flock` in `$XDG_RUNTIME_DIR`, so a timer run and a manual run never overlap.
  2. Read the tag's digest with a `HEAD` on the registry's manifest endpoint and an anonymous pull token (curl only; no skopeo). For a multi-arch release that is the index digest, which the release signs. Network failures are retried for about two and a half minutes, because a `Persistent=true` run after boot can start before the network is up, and a user unit cannot order itself after the system's `network-online.target`.
  3. Stop if the local tag's image already has that repository digest (`RepoDigests`), or if the digest failed its health check before (a per-unit state file; deleting it retries).
  4. Verify the digest: `cosign verify --certificate-identity-regexp '^https://github\.com/265866/taproot/\.github/workflows/release\.yml@refs/tags/taproot-v0\.2\.[0-9]+$' --certificate-oidc-issuer https://token.actions.githubusercontent.com --certificate-github-workflow-repository 265866/taproot`. The identity, not a key, is the trust anchor: only `release.yml` running for a `taproot-v*` tag of this repository gets such a certificate, and the certificate names that exact tag. The regexp comes from the track, so following `0.2` accepts only `taproot-v0.2.<patch>` and a moved `0.2` tag cannot bring in a prerelease or another minor version; an exact version such as `0.2.1` accepts only that tag, and any other track (such as `latest`) accepts any release tag `taproot-vX.Y.Z` but no prerelease, because `latest` never names one. Nothing compares versions, so a `0.2` tag moved back to an older patch would still install. A failure stops the run before anything is pulled.
  5. Pull by that digest, so what runs is what was verified even if the tag moves meanwhile, and pull before stopping anything, so the outage is one restart.
  6. Record the update as pending (a per-unit state file with the new, current, and previous image IDs), tag the running image `localhost/taproot:previous`, tag the new one `current`, and `systemctl --user restart` the unit. A unit someone stopped (`ActiveState` `inactive`) is only retagged. Every other state is restarted and checked like a running unit, so a crash loop is never mistaken for a stopped service: a unit that crashed and waits to restart is `activating`, one that hit its start limit is `failed`, and `is-active` calls both inactive. A crash-looping quadlet unit is also `deactivating` while `ExecStopPost` removes its container (26 of 160 samples of one on systemd 257), and so is a unit someone is stopping, so the script polls a `deactivating` unit once a second for up to 15 s and decides on the state it settles to; one still `deactivating` then counts as running. A `failed` unit that someone stopped with an unclean exit is restarted too: on systemd 257 its `Result` (`exit-code`) matches a unit that hit its start limit, and only `NRestarts` differed, which a unit that crashed earlier also has.
  7. Wait until the `TAPROOT_HEALTH_TIMEOUT` deadline (120 s, measured by the clock rather than counted in attempts) for the container to run the new image ID and the health URL (`/healthz`, which the access guard exempts) to answer. Checking the image ID matters: a restart that fails can leave the old container answering.
  8. On success, clear the pending record and remove the image that was `previous` before, if nothing else uses it, so updates do not pile up images. On failure, record the failed digest, retag the old image `current` and the old `previous` back, restart, and wait for health again. If the rollback is healthy, remove the failed image and exit 1; if it is unhealthy too, keep the failed image, exit 2, and name the unit to check. Either way the pending record is cleared.
  9. A run killed between steps 6 and 8, by a shutdown in the 04:00 window or a stopped service, leaves the pending record behind, and the new release may then start at boot without a health check. The next run handles that record before anything else: it restarts the unit if the container still runs the old image, then does step 7 and step 8, or finishes an interrupted rollback. If someone stopped the unit, it drops the record, as in step 6. A unit that crash-loops on the new release is not stopped, so it is restarted, checked, and rolled back.
- **cosign.** The script downloads cosign v3.1.4 (`cosign-linux-amd64` or `-arm64`) into `$XDG_DATA_HOME/taproot-update/` on first use and checks it against a SHA-256 pinned in the script, on every run. Both pinned binaries were checked against their Sigstore bundles (signed by `keyless@projectsigstore.iam.gserviceaccount.com`). `COSIGN=` in the settings uses another binary. cosign 3 checks the index digest against the GitHub build provenance attestation that `release.yml` attaches as an OCI referrer, and a platform digest against the legacy `.sig` signature; both are keyless and carry the same workflow certificate, so the pinned identity covers either.
- **Measured** on moss on 2026-11-08 with a throwaway unit (`systemd-run` running the `0.2.0-rc.*` images on a loopback port, a 100 ms health poller alongside): rc.1 to rc.2 verified, pulled, and restarted with 553 ms without a healthy answer; a forced rollback (a health URL that failed only on rc.3) restarted twice with gaps of 447 ms and 451 ms and restored both tags; an unsigned `docker.io/library/busybox` and a `ghcr.io/sigstore/cosign/cosign` image signed by another identity were refused with nothing pulled. Verifying and pulling took about 5 s while the old container kept serving. `--check` reports the same decisions without downloading, pulling, tagging, or restarting. With the track-bound identity, `--check` verified `0.2.0-rc.2` and `0.2.0-rc.3` each under its own exact track, and cosign refused the `0.2.0-rc.2` digest under the `0.2` and `0.2.0-rc.3` identities.
- **Schedule.** The timer runs at 04:00 server time with up to 15 minutes of random delay and `Persistent=true`, because a restart cuts streams in flight on the proxy.

## Taproot API contract (`/taproot/api/v1`)

- All endpoints return JSON.
- Times are RFC 3339 UTC.
- Time ranges use `from` and `to` query parameters (RFC 3339), and `bucket` is one of `5m|1h|1d`.
- Errors are `{error: {code, message}}`. A path under the prefix that matches no route, or matches one only under another method, gets 404 `not_found`. gin's redirect of a trailing slash (`/settings/` to `/settings`) is upstream's engine setting and still answers 301 before any middleware.

| Method and path | Response |
|---|---|
| `GET /me` | `{login, displayName, node, nodeId, via, proxy, admin}` |
| `POST /claim` | Body `{code}`, the setup code from the log, with or without its dash, in any case. Reachable by a tailnet device without Admin only while no device has Admin (see "First run"). Gives the calling device Proxy and Admin and returns `{claimed: true, device: {id, name, proxy, admin}}`. Errors: 403 `wrong_code`, 403 `claim_tailnet_only` (loopback, `access.addresses`, the server's own node, or no stable ID), 403 `claim_own_tailnet_only` (a device outside the server's tailnet), 409 `claimed`, 429 `rate_limited` after 5 wrong codes in a minute from the device or 30 from all devices (`retryAfter` in whole seconds, plus a `Retry-After` header), 503 `server_node_unknown` while tailscaled's status cannot be read and was never read, 400 `invalid_body` |
| `GET /access/devices` | `{enabled, version, devices: [{id, name, label, dnsName, login, ownerName, tags, os, created, outside, online, lastSeen?, addresses, server, onTailnet, missingSince, proxy, admin}], requests: [{nodeId, login, ownerName, name, client, firstSeen, lastSeen, count, outside, asked}], addresses: [{cidr, note}], tailnetError?, forgetAfterHours}`. `name` is empty when Tailscale hides it; a device's `addresses` are its Tailscale IPs, IPv4 first, and empty for a device the read did not list (the page shows a request's IP from its device's entry); a request's `name` is the name the device gave itself, else its Tailscale name, and its `asked` is `admin` when the device was refused the dashboard, else `proxy`. Requests are the open ones, newest first. `version` identifies the device and address lists, as in `GET /settings`. See "Access". |
| `POST /access/request` | Body `{name}`, optional. The calling tailnet device without Admin asks for access; grants nothing. Returns `{status: "pending"}`. Errors: 403 `request_tailnet_only` (loopback), 403 `request_header_required`, 409 `has_access` (the device has Admin), 400 `invalid_name`, 429 `rate_limited` after 10 in an hour for the device (`retryAfter`, plus `Retry-After`) |
| `POST /access/requests/:nodeId/dismiss` | Denies an open request: `{dismissed: true}`, or 404 `not_found`. The device's next refusal or request reopens it |
| `POST /access/requests/:nodeId/allow` | Marks the device's request allowed, open or not, after the Allow form saved its grant: `{allowed: true}`, or 404 `not_found` when the device has no request. Refusals then leave it closed; only the device's own request reopens it. Admin only, behind the same browser checks as dismiss |
| `GET /accounts` | `{accounts: [{authIndex, provider, label, email, plan, disabled, removed, removedAt, firstSeen, lastSeen}]}`. Removed accounts stay listed for labels; pools skip them. |
| `GET /quota/current` | `{accounts: [{authIndex, provider, windows: [{window: "five_hour"\|"seven_day"\|"seven_day_opus"\|"codex_primary"\|"codex_secondary"\|..., utilization (0..1), resetsAt, status, observedAt, periodSeconds}]}]}` |
| `POST /quota/refresh` | Body `{authIndex}`. Polls that account's usage endpoint now and returns `{authIndex, provider, windows}`, with windows shaped as in `/quota/current`. Each account can refresh once per 30 s; a faster request gets 429 `{error: {code: "rate_limited", message, retryAfter}}` (whole seconds) and a `Retry-After` header. Other errors: 404 `not_found`, 400 `unsupported_provider` (Claude and Codex only), 502 `upstream_failed` |
| `GET /quota/series?from&to&provider` | `{series: [{authIndex, provider, window, periodSeconds, points: [{t, utilization}], resets: [t]}]}` |
| `GET /usage/summary?from&to&bucket&groupBy=model\|account\|provider\|session\|device&tz` | `{totals: Totals, buckets: [{t, groups: {[key]: Totals}}]}`. With `groupBy=device`, events without a device group under `(none)`. `tz` is an IANA zone; with `bucket=1d`, each day starts at that zone's midnight, or at the clock change on a date that skips midnight, and other buckets ignore it. |
| `GET /requests/summary?from&to&bucket&tz&top` | Client requests (see "Client requests" under "Ingest"), with buckets as in `/usage/summary`: `{totals: {requests, failed, failureRate, retries, medianLatencyMs, medianTtftMs, costUSD, unpricedModels?}, buckets: [{t, requests, failed, failureRate}], topDevices: [{deviceId, name, requests, failed, costUSD}], topModels: [{model, requests, failed, costUSD}], firstRequestAt}`. `firstRequestAt` is the start of the oldest recorded client request (one indexed `MIN(ts)`), or null before the first; a server upgraded from 0.4 records client requests only from the upgrade on, so the Dashboard says when counting began when a window starts earlier. `retries` sums each request's attempts beyond the first; a request with unknown attempts counts none. `medianLatencyMs` and `medianTtftMs` cover only requests that reached an account (attempts above 0, or unknown), leaving out refusals before any account, which answer in microseconds, and abandoned (499) requests, whose timings say when the client gave up; `requests` and `failed` still count both. `failureRate` and the medians are null without requests to cover; medians come from log-bucketed histograms (within about 5%). `costUSD` is the window's API-equivalent usage cost, in total and for each device and model; `unpricedModels` lists the models it leaves out. `top` (1 to 50, default 5) bounds both lists, ordered by requests, then failures |
| `GET /requests/recent?failed&limit` | `{requests: [{ts, deviceId, deviceName, path, model, provider, status, failed, errorCode, errorMessage, attempts, latencyMs, ttftMs, requestId}]}`, newest first by start. `failed` is `true` or `false` to filter; `limit` is 1 to 100, default 5. `requestId` opens the request in Request Logs, and is null when no log is stored; `attempts` is null when unknown |

## Decisions

- **Data from before taproot.** The code has no importer and no format converter. When the first deployment replaced CLIProxyAPI and CPA Usage Keeper on 2026-11-03, their history from 2026-09-18 on (request logs, usage, and quota) was imported once with a one-off tool that is not in the repository; the earlier Usage Keeper importer (`cmd/taproot-import`) was removed. Its request logs in the first storage format were converted to the current format in place on 2026-11-07, also once, and the code reads only the current format.
- **Request log segments.** Segments roll on idle (15m), age (6h), day change, or 128 MiB stored, not hourly. On the real fixture, per-session segments compressed 97x, while per-session-hour segments compressed 73x. On the production corpus, with blobs out, 128 MiB segments stored 1.28 GB against 1.15 GB for 256 MiB and 1.59 GB for 64 MiB; 128 MiB halves sealing and lookup memory (about 145 MB each) for 3% of the total.
- **Not adopted.** Global chunk dedup across sessions (5% for an index the size of its savings), dropping the upstream request and response copies (6%, loses what was sent upstream), lossless JPEG XL for PNGs (36% smaller but rebuilds a different PNG file), C zstd through cgo (7% over Go's best level), and xz (seconds-long lookups).
- **Plugin resource routes** (`/v0/resource/plugins/*`) are guarded but get no injected key. Upstream serves them unauthenticated and forwards headers to plugin code.
- **Status cost.** One status evaluation reads, on 1M client requests over 30 days and 30 days of quota rows for 8 accounts with 4 windows each every 5 minutes (`TestClientRequestsAtScale`, medians of 5): the last 15 minutes' counts in 1.3 ms, the last hour's in 6.5 ms, the latest quota in 0.4 ms, and 9 hours of quota history in 13 ms, about 21 ms in all. The Dashboard reads the three endpoints every 30 s while visible and the module evaluates once every 30 s, so nothing is cached; the endpoints never touch the request path.
- **RESP usage queue.** Upstream multiplexes this Redis-protocol queue on the proxy port, outside gin, so the guard never sees it, and the generated `MANAGEMENT_PASSWORD` enables remote `AUTH`. The security recheck (F2) showed a tailnet peer authenticating with the secret. Taproot does not use the queue, so the RESP connection filter (see "Upstream boundary") closes every RESP connection that does not come from loopback, before any reply. Drop the hook if upstream adds a switch to disable the queue.
- **Poller timeout.** The idle-account poller's 30 s timeout on its read-only usage probe is an intended exception to the no-timeout rule in `CONTRIBUTING.md`. That rule targets proxied upstream traffic. The alerts module's reset-grant read (30 s) and Discord webhook POST (15 s) are exceptions for the same reason.
- **LGPL crates.** The codec library statically links `cabac` (LGPL-3.0-or-later), which `preflate-rs` uses, so the image and every `taproot_codecs` build convey an LGPL library inside a combined work. Taproot meets LGPL-3.0 section 4 with option 4(d)(0). `THIRD_PARTY_NOTICES.md` opens with a section that names each LGPL crate, its crates.io source and `Cargo.lock` checksum, the release source archives, and the steps to rebuild with a modified copy through a `[patch.crates-io]` entry and `internal/taproot/reqlog/codec/native/patches/`, which the image's codec stage copies. The LGPL and GPL texts ship in `licenses/` and the image's `/taproot/licenses/`. `scripts/taproot/third-party-notices.ts` writes that section for every crate whose license expression requires the LGPL v3 (`scripts/taproot/copyleft.ts` evaluates the SPDX expression), and it stops on any other copyleft license it recognizes, strong or weak (the GNU family, MPL, EPL, CDDL, EUPL, and the others `copyleft.ts` lists), in any ecosystem, until someone decides how taproot complies.
- **Image.** `Containerfile.taproot` pins each base image to its multi-arch index digest, keeping the tag for readability, and labels the image with OCI `source`, `version`, `revision`, `licenses`, `title`, and `description`. The runtime stage ships `LICENSE`, `THIRD_PARTY_NOTICES.md`, `web/LICENSE`, and `licenses/` in `/taproot/`, at the paths the notices link to.
- **Releases.** release-please keeps a release PR on `main` and, when it merges, tags `taproot-vX.Y.Z` and creates a draft release; `.github/workflows/release.yml` builds the tag and publishes the release only once its files are uploaded, so a published release always has them. `CONTRIBUTING.md` describes the flow.
  - The Fulcio certificate of each signature and attestation names `https://github.com/265866/taproot/.github/workflows/release.yml@<ref>`, where `<ref>` is the ref the run started on, and the documented `cosign verify` and `gh attestation verify` accept only `@refs/tags/taproot-v`, so a release build must start on its tag. release-please creates the tag with `GITHUB_TOKEN`, which starts no workflow for the tag's push, so the `release` job of `release-please.yml` starts `release.yml` on the tag with `workflow_dispatch`, which `GITHUB_TOKEN` may start. It needs only `actions: write`. It does not call `release.yml` as a reusable workflow (`workflow_call`): a called workflow's certificate takes its ref from the caller's `job_workflow_ref`, which is `refs/heads/main`, so a release built that way would fail the documented check. A tag pushed by a person, such as a release candidate, starts `release.yml` itself. The first step of `release.yml` refuses a run whose ref is not `refs/tags/<tag>`, and the publish job verifies its own signature and attestation against the exact identity of its tag.
  - Each architecture builds on its own native runner (`ubuntu-latest`, `ubuntu-24.04-arm`) and pushes by digest; one job joins the two into an index under the version tag only, attests, signs, and verifies it, and only then adds `sha-<commit>`, `X.Y`, and `latest` by copying the signed index, so a failed signing never leaves a floating tag on an unsigned image. A version with a `-` suffix is a prerelease and gets only its own tag and `sha-<commit>`, so `X.Y` and `latest` never move to a candidate. A release gets `X.Y` only when no newer `X.Y.*` release is tagged, and `latest` only when no newer release is, so re-running an old release or fixing an older line never moves them back. `scripts/taproot/release-version.sh` derives the tags from the tag being built and the existing release tags, and `scripts/taproot/release-notes.sh` takes the notes from `CHANGELOG.md`. The first job checks the notes, so a release tag without a section stops before anything is pushed.
  - release-please reads commits with GraphQL `history`, which walks the whole ancestry and has no first-parent option, so after an upstream sync it would list every upstream `feat` and `fix` as taproot's, with `(#NNNN)` links to taproot issues that do not exist. `skip-changelog` keeps its section out of `CHANGELOG.md`, and the `changelog` job of `release-please.yml` writes the section with `scripts/taproot/release-changelog.sh` instead. That script lists the commits since the previous release that are not ancestors of the newest upstream snapshot (`latest_snapshot` in `upstream-lib.sh`), which leaves taproot's own commits, including those of a pull request merged with a merge commit, and adds one line naming the upstream commit when the release includes a sync. The version still counts upstream commits; before 1.0 that raises at most the minor version, and a `Release-As` footer overrides it. `scripts/taproot/release_test.go` covers the three scripts.
  - cosign 3 signs in its legacy format (`--new-bundle-format=false`), which stores the signature under the registry's `sha256-<digest>.sig` tag rather than as an OCI referrer, so a verifier that reads only tag-based signatures still finds it. `--recursive` also signs each platform's manifest, so a client that resolves the index to one platform can verify the image it pulls. GitHub's build provenance attestation is pushed to the registry as well, for `gh attestation verify`.
  - The tarballs are copied out of each pushed image, so the binary in a tarball is the image's, and they carry the image's license files, including the LGPL texts the codec library requires (see LGPL crates). Their mtimes are the commit time and gzip stores no timestamp. The binary links dynamically against the glibc of the runtime base, Debian 12, and needs glibc 2.34 or later, so the release notes state the oldest glibc version the binaries need, which the publish job reads with `readelf`.
  - The Lepton format must read the same on both architectures, because a backup can move between hosts. The release runs the codec tests on each architecture, which decode the committed stored bytes written on amd64, and then each architecture decodes the bytes the other just stored. A failure there stops the release before any tag moves.
  - Release builds use no build cache, so nothing another workflow wrote can change what ships.
- **Shutdown drain.** On SIGTERM or SIGINT, upstream's service stops and closes the HTTP server without draining it, and `main` then calls the shutdown function `Setup` returned (see "Upstream boundary"). It cancels the modules and waits for the request-log writer, which writes the records still in its 8192-entry queue, and for ingest's writer, whose final flush writes the usage events queued since its last flush (it flushes every second) and every queued client request, without the 2-second wait for late usage records. A process killed without a signal loses those queues; the request-log records already in an open segment are re-indexed on the next start. Requests still running when the server closes are cut, and their records may be lost.
- **Mounts.** `config.yaml` lives in the mounted data directory, which is what restore's atomic rename needs. The host's tailscaled folder must be mounted at `/var/run/tailscale`, so the socket is at `/var/run/tailscale/tailscaled.sock` (see "Install examples"). After deploying, `GET /taproot/api/v1/me` from a tailnet device with Admin must report `via: "tailnet"` and `admin: true`, and the same request from a device without Admin must get 403 `not_admin`. If it reports loopback, the port forwarding is rewriting source addresses and the guard would admit everyone. From the server host itself, `curl http://100.64.0.1:8317/taproot/api/v1/me` (with the host's Tailscale address) must return 403 and `curl http://100.64.0.1:8317/v1/models` must not, which shows the server's own node is proxy-only. A `127.0.1.1:8317` publish, from the host, gets 403 on both unless the host's LAN address is in `access.addresses` (see "Security model").
- **Install examples.** The README's Quick start and `docs/install.md` install the published image and follow one minor tag, `ghcr.io/265866/taproot:0.5`, which brings patch releases and never a minor version, which can rename `taproot.yaml` keys (see `docs/stability.md`). `examples/taproot/compose.yaml` and `examples/taproot/taproot.container` run that tag. The quadlet switches to the local tag `localhost/taproot:current` only when the operator turns on `scripts/taproot/taproot-update` (see "Automatic updates"), so a new user's install and manual update need no local tag. Neither file pulls an image the host already has: the default update is a manual pull and restart, because a restart cuts streams in flight. The NixOS example pins a release tag of the flake, because an unpinned `github:` input follows unreleased commits on `main`. The compose file mirrors the quadlet's read-only root, dropped capabilities, and Tailscale-only publish, adds the `/tmp` tmpfs that Podman gives a read-only container and Docker does not, and runs as the data directory's owner, because rootful Docker maps no user namespace.
  - Both files and the Quick start mount the host's folder `/var/run/tailscale` read-only, not the socket file. A bind mount of a file pins its inode, so after tailscaled restarts the container still sees the deleted socket and every whois fails until taproot restarts (measured with throwaway mounts, and the cause of an outage on a server). A folder mount sees the new socket only while the folder itself survives, and Debian's and Tailscale's own tailscaled units set `RuntimeDirectory=tailscale` without `RuntimeDirectoryPreserve`, so systemd deletes and recreates `/run/tailscale` on every stop and start (the server's `/run/tailscale` was born at the restart). `docs/install.md` therefore has the operator add a drop-in with `RuntimeDirectoryPreserve=yes`, which keeps the folder's inode across restarts (checked with probe units: the same inode with `yes`, a new one with `no`). Mounting `/run` would survive without it but would hand the container every other socket there. A connect to a socket needs no write access to the mount, so `:ro` costs nothing. The access monitor (see "tailscaled while running") reports the failure if either setting is missing.
  - `examples/taproot/taproot.service` runs the release tarball's binary outside a container. It copies the NixOS module's defenses (see "Nix"): `IPAddressDeny=localhost`, because every local process is a loopback caller, and a config that listens on the Tailscale address. `IPAddressDeny` also drops DNS to a loopback stub, and Debian and Ubuntu with systemd-resolved point `/etc/resolv.conf` at `127.0.0.53` with `hosts: files dns`, where Go's resolver and glibc both read that file. The unit bind-mounts resolved's upstream list, `/run/systemd/resolve/resolv.conf`, over `/etc/resolv.conf` when it exists (checked in a `systemd-run` transient unit on Debian 13: the lookup used the upstream server). Allowing `127.0.0.53` instead would let a local process that binds that source address reach taproot as loopback.
