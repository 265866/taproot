# taproot dashboard

The dashboard taproot serves at `/` on its proxy port. It is a React 19 and TypeScript app, built with Vite into `index.html` and hashed chunks under `assets/`, which the Go server embeds.

It started as a fork of the [CLIProxyAPI Management Center](https://github.com/router-for-me/Cli-Proxy-API-Management-Center) and no longer follows it. It has no login page and holds no key: taproot's access guard decides who reaches it. The [repository README](../README.md) and the [documentation](../README.md#documentation) cover taproot itself, and the "Web" and "Dashboard scope" sections of [`internal/taproot/DESIGN.md`](../internal/taproot/DESIGN.md) cover how the server serves the dashboard and what it includes. The dashboard keeps the Management Center's [MIT License](LICENSE).

## Commands

Use Bun; the `packageManager` field in `package.json` pins its version. Keep dependency changes in `bun.lock` and add no other package manager's lockfile.

```sh
bun install --frozen-lockfile
bun run dev      # Vite at http://localhost:5173, proxying to a local taproot
bun run verify   # tests, lint, and the production build
```

- `bun run dev` proxies `/v8`, `/v0`, and `/taproot` to `TAPROOT_DEV_SERVER` (default `http://127.0.0.1:8317`). With the guard off (`access.enabled: false`), nothing injects the management key, so start the server with `MANAGEMENT_PASSWORD=<key>` and set `TAPROOT_DEV_MANAGEMENT_KEY=<key>` for Vite; the proxy adds the header in development only.
- `bun test tests/apiError.test.ts` runs one test file.
- `bun run type-check` covers `src` only, not `tests`.
- `bun run format` formats all of `src`. Several files from the Management Center are not Prettier-clean, so prefer formatting only the files you change.
- `bash ../scripts/taproot/build-web.sh` builds the dashboard and copies it to `internal/taproot/web/dist/`, where the server embeds it.

## What the dashboard talks to

It calls two same-origin APIs and never holds a credential:

- The CLIProxyAPI v8 Management API under `/v8/management`. Taproot's guard admits allowlisted Tailscale callers and injects the management key server-side, so requests carry no `Authorization` header. Do not add v0 fallbacks or legacy config adapters. Plugin resources and custom HTTP extensions keep their backend-declared paths.
- Taproot's own API under `/taproot/api/v1`, through the typed client in `src/services/api/taproot.ts`. Its contract is in `DESIGN.md`.

There is no login page, management-key prompt, or key storage. `src/router/ConnectionGate.tsx` connects once and shows progress, access denied, or server unreachable. A tailnet device without Admin sees `src/router/RequestAccessScreen.tsx`, which asks for access with `POST /taproot/api/v1/access/request`; while no device has Admin, it sees `src/router/ClaimScreen.tsx` instead, which sends the setup code from taproot's log to `POST /taproot/api/v1/claim`. `src/utils/legacyStorage.ts` deletes keys the Management Center left in localStorage on the same origin.

Removed for good: Quick Start, AI Providers and API-key provider editing, sponsor or affiliate content, Kimi China, Devin, Vertex, SIWC, Config panel API-key editing, non-English locales, and System's "Check for updates" button (it compared taproot's version with CLIProxyAPI's releases). Their backend code stays in the Go tree; only the dashboard drops them.

- Treat the backend as the source of truth. Read the Go code before changing endpoint names, payloads, provider keys, OAuth callback parameters, auth-file semantics, or plugin and config contracts.
- Use `apiClient` from `src/services/api/client.ts` for Management API requests, through domain modules. It centralizes the API prefix, error normalization, and response headers. Use `taprootApi` for taproot endpoints. Components make no ad hoc requests.
- Keep the clients' events: `unauthorized` (a 401 from either client) marks the connection as access denied, `taproot-admin-revoked` (a 403 `not_admin`) reconnects so the gate can ask for access, `server-version-update` carries version and build metadata, and `server-plugin-support-update` carries plugin capability. Plugin routes and nav items stay gated by backend support.
- Normalize backend fields on read and serialize them on write in the API layer (`transformers.ts` and the domain modules), not in UI components.
- `useConfigStore.fetchConfig(forceRefresh?)` caches the full config with a TTL and deduplicates requests in flight. Reuse it, and update or invalidate the cache after a mutation with the store's actions. `invalidate()` forces the next read but keeps the last good config on screen; `clearCache()` with no section also drops it, for a new connection.
- A page joins the header's Refresh All with `useHeaderRefresh(handler)`. The handler resolves to an outcome (`REFRESH_OK`, `refreshFailed(error)`, `REFRESH_CANCELLED` when the user keeps a draft, or `REFRESH_STARTED` when the page shows its own results) rather than swallowing a failure, so the header reports what happened. Only the current page layer's handler runs.
- `useUnsavedChangesGuard` asks before in-app navigation, an edited hash, a reload, or a tab close loses a draft. The edited-hash half listens ahead of the router (`installEditedHashGuard` in `App.tsx`).
- Keep stale-request guards (`apiClient.getConnectionRevision()`) around read-modify-write sequences.

## Layout

- `src/features/`: feature-owned pages, components, hooks, types, and logic: `dashboard`, `accounts`, `authFiles` (credential data hooks, the details form, and policy editors under `policy/`), `oauth` (provider sign-in flows), `routing` (OAuth credentials only), `config`, and `plugins`.
- `dashboard` (`#/`) is the home page. `hooks/useDashboardData.ts` runs its one poll and keeps each read's last good data; `model/` holds the pure parts the tests cover (the window and its buckets, formatting, the chart's geometry, the action each Needs-you item offers, the links into other pages, and the first-run steps); `DashboardView` renders a set of reads, so tests render the page without the poll; `components/` draws the verdict, Needs you, Pools, the window's tiles and chart, the failures, and the top lists. It links into other pages with query parameters those pages read once: Accounts `?provider=` and `?signIn=`, Access `?focus=<node ID>`, Settings `?section=alerts`, and Request Logs' and Usage's own filters. `src/router/deepLinks.ts` holds the readers each page uses, which the tests check against the Dashboard's links. `src/hooks/useFocusOnArrival.ts` scrolls to and focuses the item such a link names.
- `accounts` (`#/accounts`) is one page for every account. It composes other features rather than owning their logic: the pool charts and ledger from `taproot-quota`, credential actions from `authFiles`, and sign-in from `oauth`. Its `model.ts` joins taproot's accounts with the credential files; once the file list loads, it decides which accounts exist and which are enabled. `#/quota`, `#/auth-files`, and `#/oauth` redirect there (`LEGACY_REDIRECTS` in `src/router/routes.ts`).
- `src/features/taproot-{quota,usage,logs,backups,access,settings}/`: taproot's sections. `taproot-access` is the Access page: access requests, tailnet devices with their names and their Proxy and Admin switches, and addresses without Tailscale. `taproot-quota` has no page of its own: Accounts renders its pool charts and ledger. It keeps its pure projection model in `model/` and the live provider adapters in `live/`. `taproot-logs` also holds the application log tail (`appLogs/`, the `?tab=app` tab of `#/request-logs`).
- `src/pages/`: route pages outside the feature layout: System, and the OAuth excluded-model and model-alias editors at `#/routing/oauth-excluded` and `#/routing/oauth-model-alias` (Routing lists the rules).
- `src/components/`, `src/hooks/`, `src/utils/`: shared UI, hooks, and utilities. Feature-specific code stays in its feature.
- `src/services/api/`: API clients, domain endpoints, and backend data normalization.
- `src/stores/`: Zustand state. `useAuthStore` holds the connection state (status, failure reason, server version, plugin support), not credentials.
- `src/App.tsx` sets up the hash router. `src/router/routes.ts` holds the route paths that the route table (`MainRoutes.tsx`), the sidebar, and links share. `src/components/layout/MainLayout.tsx` is the shell and sidebar.

## Shell

- **Sidebar.** A 200px column of 30px items in two groups, under a 28px mark and a 16px wordmark. Its footer holds the Show emails switch (`src/components/layout/ShowEmailsSwitch.tsx`; see "Account emails"), then the version and the theme menu. One-line labels cut with `@include clip-line` (`src/styles/mixins.scss`), which clips sideways only: a font taller than the line box, such as Segoe UI or Noto Sans, keeps its descenders; `tests/sidebarShell.test.ts` checks every cut sidebar label. Ctrl+B (⌘B on a Mac) collapses it to an icon rail. On phones it is a drawer: it traps focus, closes with Escape or its own close button, and returns focus to the menu button.
- **Page header.** `src/components/layout/PageHeader.tsx` is the row above every page: the page's name on the left (the bar's title on phones, with the menu button), and on the right "updated 8 s ago · refreshes every 30 s" and the Refresh All button. It is sticky, and the shell writes its height to `--header-height`, so a page's own sticky bars sit at `top: var(--header-height)`. A page shows when its data loaded with `usePageFreshness(updatedAt, intervalMs)` (`src/hooks/usePageFreshness.ts`); only the current page layer claims the stamp, and leaving the page clears it.
- **Stacking.** The phone drawer and its backdrop sit at `$z-dropdown - 1`, the page header at `$z-page-header`, and a page's sticky bars at `$z-page-sticky` (`src/styles/variables.scss`). A page's sticky bar comes after the header in the document, so at the header's z-index it would paint over the header's buttons; `tests/shellStacking.test.ts` compiles every SCSS file and fails on a sticky bar at or above the header.
- **Page rail.** A page renders `<PageAside label="…">` (`src/components/layout/PageAside.tsx`, with its state in `pageAsideStore.ts`) to fill a full-height rail beside its header and content. In a window at least 1192px wide (`$breakpoint-page-aside`: the open sidebar, the rail, the scrollbar lane, and 640px for the page), the header and the page take the left column and the rail, `--page-aside-width` (344px) wide with a hairline on its left, spans the window's height, grows with its content, and scrolls with the page. In narrower windows and on phones it follows the header inline, before the page, as it does in the document. A page whose data loads after its first paint can render its rail inline at its own top below `$breakpoint-page-aside` instead, as the Dashboard does, so the rail mounts with the page instead of pushing down a page that already painted; a page that wants something above the rail there, such as the Dashboard's verdict, renders it at the top of the rail below `$breakpoint-page-aside` and in the page above it. Show one copy by default and swap them only inside `@media (min-width: $breakpoint-page-aside)`: a zoomed window can be a fractional width that a `max-width: … - 1px` query misses. The rail draws no padding, so its content owns its spacing. The page transition and its layers clip only vertically, and sideways only while a horizontal slide runs (`.main-content` clips sideways at the window's edge), so an inline rail can run its hairlines through the page's gutters with negative margins. A rail that remounts as it crosses the breakpoint loses its own state and focus, so keep state a control's result needs in the page, and give the focus back as the Dashboard's `useKeepFocus` does; it also moves the focus between two copies of a control, such as the verdict's, when one hides and the other shows. Pages without one keep the full width. Only the current page layer claims the rail. Under `bun run dev`, `?demo-aside` before the `#` shows a sample rail beside every page; production builds leave it out.
- **Attention.** `src/stores/useAttentionStore.ts` holds what needs the user: a badge per nav item (`{ severity, count?, label }`, drawn as the count or "!"), and a count that puts "● " before the tab title and a number on the phone menu button. `src/stores/useAttentionFeed.ts` fills it: the shell runs `useAttentionFeed` once, which reads `GET /taproot/api/v1/attention` every 30 s while the tab is visible, on each page change, and when credentials change, keeps the last good badges when a read fails, and holds the list in `useAttentionFeedStore` for the Dashboard, so the page never reads it twice. Under `bun run dev`, add `?demo-attention` before the `#` (`http://localhost:5173/?demo-attention#/`) to load the sample in `src/stores/demoAttention.ts` instead; production builds leave it out.

## Text

The UI is English only, and the i18n layer stays: user-facing text, including accessible labels, goes in catalogs.

- Each feature owns `src/i18n/locales/en/<feature>.json`. A file owns its top-level keys (`taproot-usage.json` owns `taproot_usage`), and call sites use `t('taproot_usage.title')`.
- `src/i18n/resources.ts` merges every file in that folder at startup with `import.meta.glob`, so a new file needs no registration. Two files that define the same top-level key throw at startup.
- Shell strings (nav, sidebar, header, theme, connection gate) live in `shell.json`, the console primitives' strings (the updated stamp, Retry, Stale, severity words) in `console.json`, and strings several features share in `common.json`.
- Tests read the merged catalog with `import { en } from '@/i18n/resources'`. `bunfig.toml` preloads `tests/helpers/viteGlobPlugin.ts`, which expands the same glob under `bun test`, and `tests/helpers/viteDefines.ts`, which stands in for Vite's `define` constants such as `__APP_VERSION__`.

## Build output

The build emits only `index.html` and content-hashed JS and CSS chunks under `assets/`; `scripts/taproot/build-web.sh` refuses anything else. Images stay inlined in the chunks that use them. Each route page is its own chunk (`src/router/pageImports.ts`), and `main.tsx` starts loading the current page's chunk before the connection gate answers. Keep hash routing. Do not edit the generated `dist/` files. The app version, `__APP_VERSION__`, comes from `VERSION`, then a `taproot-v*` git tag, then the package version, and falls back to `dev`.

## Visual style

The dashboard is monochrome: a pure black page where cards are the page color, separated by 1px hairlines. The shell and the console pages are dense, with 13px body text and compact rows; display numerals stay for pages that have not moved to the console primitives yet. The interface has no hue of its own. A neutral gray marks selection and focus, and the primary button is near-white with black text. Provider and status colors are the only color on the page. Dark is the default theme; the light, white, and auto themes get the same neutral treatment (gray pills, a near-black primary button) and must keep working. Use the tokens in `src/styles/themes.scss`, not hard-coded colors:

- Surfaces and text: `--bg-secondary` (page), `--bg-primary` (cards; pure black in dark, so a card needs its `--border-color` hairline), `--bg-tertiary` and `--bg-hover` (hover, active), `--floating-surface` (menus, popovers, tooltips; a step lighter with a border so they read as floating), `--border-color`, `--text-primary`, `--text-secondary`, `--text-tertiary`, and `--input-bg`. Text tokens meet WCAG AA on every surface in every theme; `tests/themeContrast.test.ts` enforces it.
- Neutral accent: `--accent` (focus outlines, toggles, checkboxes, the selected tab underline), `--accent-hover`, `--accent-subtle` (selected pill fill), `--accent-text` (selected text), `--accent-border`, and `--focus-ring`. `--primary-color` maps to `--accent`; `--primary-contrast` is the ink drawn on it, such as a checked toggle's thumb.
- Links are not colored, so a text link needs an underline, or a trailing arrow and heavier weight as panel links use.
- Selection: a selected tab's underline uses `--accent`; a selected segment or chip uses `--accent-subtle` with `--accent-text`. Never mark a selection or a primary action with a `--text-primary` fill.
- Provider colors: `--provider-claude`, `--provider-codex`, and their `-soft` fills, reserved for provider data. Chart series use muted cool hues that keep clear of them and of the status colors, so Claude orange is the only warm series; `tests/usagePalette.test.ts` checks this and the series' separation.
- Status: `--status-ok`, `--status-warning`, `--status-danger`, and `--status-info`, each with `-text`, `-bg`, and `-border`. The bare token is an ink for icons and dots (3:1 on every surface); `-text` meets AA on every surface and on its own `-bg` tint. Info is neutral, as the interface has no hue. Mark state with these, never with a provider color; `tests/themeContrast.test.ts` checks the ratios, that warning and danger stay apart, and that no status token borrows a provider color.
- Console type scale, named by role: `--fs-tag` (10.5px: tags, sidebar group labels), `--fs-small` (11px: badges, table headers), `--fs-caption` (11.5px: tile labels and sub-lines), `--fs-meta` (12px: captions, links, stamps), `--fs-table` (12.5px), `--fs-body` (13px), `--fs-title` (15px), `--fs-verdict` (20px), and `--fs-stat` (22px), with `--lh-tight` and `--lh-body`. Below `$breakpoint-mobile`, and on a coarse pointer no taller than 500px (a phone held sideways), the tokens step up for phones: `--fs-tag` and `--fs-small` to 11px, and `--fs-caption`, `--fs-meta`, and `--fs-table` to 13px. On a coarse pointer (`@media (pointer: coarse)`), controls are at least 44px at any width, `.btn-sm` included; a module's compact size must not cancel that, so query `(max-width: $breakpoint-mobile), (pointer: coarse)` together. Spacing: `--space-1` to `--space-7` on a 4px grid, `--console-gutter` (the content column's side padding), and `--console-gap` (between sections).
- Display type: `--font-size-page-title`, `--font-size-numeral-xl`, `--font-size-numeral-lg`, and the `.numeral-xl` and `.numeral-lg` classes.
- Primary actions, including feature-owned pills, use `--button-primary-bg`, `--button-primary-hover`, and `--button-primary-text`. Toggles and checkboxes use `--primary-color`.
- The taproot mark: `src/components/common/TaprootMark.tsx` draws the bare glyph in `--mark-color`. Only the favicon (`src/assets/taprootMark.ts`, repeated in `index.html`) sits on a dark tile.

Charts use Recharts. Reuse the components in `src/components/ui/` before adding primitives. The console primitives, which the Dashboard uses and other pages can adopt:

- `StatTile` and `StatGroup`: a label, a value, a sub-line, and an optional status `tone`, in one hairline frame (four across, two by two on phones). `loading` shows placeholders.
- `Section`: a titled block with a caption, a right-side `action` link, and its body in a card. It handles its own states: `loading` without content shows a skeleton; `error` without content takes the body with a Retry button (`onRetry`); `error` with content keeps the last good data under the error and marks it Stale; `stale` marks it without an error; `unavailable` without content says "Not loaded" quietly, for a page that shows one error and one Retry for every section. It masks emails in the error text.
- `SeverityTag`: Blocking (danger), Overdue and At risk (warning), Waiting (neutral), OK. The mapping is `SEVERITY_TONE` in `status.ts`.
- `DataTable`, `DataTableHead`, `DataTableCell` (`numeric`, `mono`, `truncate`, `muted`), and `StatusPill` for a status code. Compact rows, scoped headers, tabular numbers; wide tables scroll inside their box.
- `SegmentedControl`: one choice among a few, as an ARIA radio group with one Tab stop; the arrows, Home, and End move and select.
- `UpdatedAgo`: "updated 8 s ago · refreshes every 30 s", ticking on the shared one-second clock (`SECOND_CLOCK`), or "8 s ago" with `compact`.

Sheets and modals join the layer stack in `src/components/ui/layerStack.ts`, so only the top dialog handles Escape and traps Tab; a new dialog primitive must join it too. Keep keyboard interaction, accessible names, focus behavior, and reduced-motion handling. For motion, reuse `--ease-out-strong`, `--dur-press`, `--dur-hover`, and the helpers in `src/hooks/motion.ts`.

Code style: 2-space indentation, semicolons, single quotes, ES5 trailing commas, and a 100-character line (`.prettierrc`). Use `unknown` with narrowing for untrusted data rather than `any`, and the `@/` alias for imports from `src`. Components are PascalCase, hooks `useName`, and API modules domain names such as `oauth.ts`. SCSS Modules sit beside their component as `Name.module.scss`; Vite injects `src/styles/variables.scss` into every SCSS file.

## Account emails

Emails are hidden by default everywhere. Auth file names carry the email (`claude-<hash>-<email>.json`), and so can error text, logs, bodies, and session IDs. Render any such text through `mask` from `src/hooks/useEmailMask.ts`, including `title`, `aria-label`, and DOM IDs. Toasts, confirmations, modal and sheet titles, and `Select` labels already mask strings. Search, filters, API calls, copy, and download keep the real values. Error banners and `EmptyState` text come from the server, so they are masked too; `tests/emailRedactionErrors.test.ts` scans for unmasked ones.

- A filter field whose value holds an email shows `MaskedValueChip` while emails are hidden. An edit field shows the value masked and read-only until emails are shown (see `AuthFileDetailsForm`).
- A value that can hold an email goes into the URL through `encodeUrlValue` (`src/utils/urlValue.ts`).
- While emails are hidden, a credential's raw JSON under Manage, Advanced settings also hides its tokens, secrets, and keys (`src/features/authFiles/secretMask.ts`). Copy and download keep them.
- The preference lives in `src/stores/usePrivacyStore.ts`. It starts hidden on every page load and is never stored in the browser; keep it out of `persist`, localStorage, sessionStorage, and cookies. The one switch is Show emails in the sidebar's footer: a labelled switch in the open sidebar and the drawer, and an icon button with a tooltip, its name, and its `aria-checked` state in the collapsed one. Pages carry no switch of their own; they read the preference through `useEmailMask`. Access masks owners' logins that are emails too; a login such as `alice@github` is not an email and stays readable.

The browser never receives or stores the management key. Keep keys, credentials, auth files, request logs, and backups out of fixtures and screenshots.

## Tests

Tests live in `tests/` as `*.test.ts` and use `bun:test`, with fixtures in `tests/fixtures/` and helpers in `tests/helpers/`. They cover pure logic, React static rendering through `renderToStaticMarkup`, source and contract checks, and real HTTP against `Bun.serve`. Where a behavior needs a DOM, such as focus that must survive a remount, a test registers happy-dom for its own file (`GlobalRegistrator.register()` at the top, `unregister()` in `afterAll`), imports React DOM and the components after that, and stands in for layout and `ResizeObserver` itself, as `tests/dashboardDom.test.ts` does; happy-dom lays nothing out and applies no CSS modules. Neither proves what a browser draws: load a changed page in a browser against a running server too. Server rendering also reads a zustand store's creation state, so a test cannot render a component with store state it set later; test the pieces and the wiring instead, as `tests/shellAttention.test.ts` does.
